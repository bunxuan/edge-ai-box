### 二、层间交互类详细设计（核心重点）

层间交互类是整个三层架构的"关节"。它们不归属于任何一层的业务逻辑，而是作为层与层之间的通信基础设施存在。系统共设计 5 个核心层间交互类和 4 个标准数据传输结构体。

#### 2.1 数据传输结构体

所有层间传递的数据都封装为以下四种标准结构体之一，确保层间接口类型安全、语义清晰。

```cpp
// ============================================================
// 结构体 1：视频帧对象 —— 表示层 → 业务层（帧分发队列）
// ============================================================
struct VideoFrame {
    int         camera_id;       // 摄像头 ID
    uint64_t    capture_time;    // 采集时间 (CLOCK_MONOTONIC)
    int         width, height;   // 图像尺寸
    PixelFormat format;          // NV12 / NV21 / RGB888
    uint8_t    *data;            // 图像数据指针（所有权转移）
    size_t      data_len;        // 数据字节数
    FrameOwner  owner;           // OWNED / BORROWED / TRANSFERRED
};

// ============================================================
// 结构体 2：层间消息 —— 所有层间消息的统一载体
// ============================================================
struct LayerMessage {
    MsgType     type;            // 消息类型枚举（见下方分类）
    int         camera_id;       // 关联摄像头（-1 = 不关联）
    int         device_id;       // 关联设备  （-1 = 不关联）
    uint64_t    timestamp;       // 单调时钟时间戳
    void       *payload;         // 按 type 解释为不同结构
    size_t      payload_len;
};

// MsgType 枚举分类：
//   ── 表示层 → 业务层 ──
//   MSG_SENSOR_DATA          ESP32/PLC 上报的传感器数据
//   MSG_CLOUD_CMD_*          云端管理指令（模型更新/抓图调整/日志级别/摄像头增删等）
//   MSG_LOCAL_CONTROL        本地 HTTP 收到的控制请求
//   MSG_DEVICE_EVENT         数据访问层上报的设备事件（离线/状态突变）
//
//   ── 业务层 → 表示层 ──
//   MSG_REPORT_DETECTION     AI 检测结果上报
//   MSG_REPORT_ANOMALY       异常图片待上传
//   MSG_REPORT_LOG           日志包待上传
//   MSG_REPORT_STATUS        设备状态响应
//   MSG_REPORT_CMD_RESULT    控制命令执行结果
//   MSG_REPORT_MODEL_STATUS  模型更新状态
//   MSG_REPORT_CAPTURE       定时抓拍图片待上传

// ============================================================
// 结构体 3：设备控制命令 —— 业务层 → 数据访问层（命令队列）
// ============================================================
struct DeviceCommand {
    int         device_id;       // 目标设备 ID
    CmdType     cmd_type;        // OPEN_DOOR / START_FAN / STOP_PUMP / ...
    void       *params;          // 命令参数（按 cmd_type 解释）
    uint32_t    timeout_ms;      // 超时毫秒数
    CmdResult  *result;          // [out] 执行结果回写
    sem_t      *done_sem;        // 信号量，通知业务层执行完毕
};

// ============================================================
// 结构体 4：设备状态 —— 数据访问层 → 业务层（状态缓存）
// ============================================================
struct DeviceStatus {
    int         device_id;
    DeviceType  type;            // DOOR / WATER_SENSOR / TEMP_HUMID / ...
    CommInterface iface;         // GPIO / RS485 / I2C / SPI
    bool        online;          // 是否在线
    double      value;           // 当前数值（温湿度等模拟量）
    bool        switch_state;    // 开关量状态（门禁开/关等）
    uint64_t    last_update;     // 最后更新时间戳
    int         timeout_count;   // 连续超时计数
};
```

#### 2.2 五条层间通道对应的交互类

**通道 ① — FrameDispatcher（帧分发器）**

这是表示层与业务层之间传输视频帧数据的专用通道。它本质上是一个有界环形缓冲区，内部通过互斥锁 + 条件变量实现线程安全。设计要点是"新帧覆盖旧帧"和"所有权转移"——当缓冲区满时，最旧的帧被丢弃（视频监控场景下最新帧永远比旧帧更有价值）；帧写入队列后，表示层放弃所有权，业务层取出后成为唯一持有者，避免内存拷贝开销。

```cpp
class FrameDispatcher {
public:
    // 构造时按平台预分配容量：RK3568=16, RK3576=48, RK3588=64
    explicit FrameDispatcher(int max_camera_count);
    ~FrameDispatcher();

    // 表示层调用：写入一帧，若队列满则丢弃最旧帧
    // 写入后 frame->owner 变为 TRANSFERRED，表示层不再持有
    void push(VideoFrame *frame);

    // 业务层 FrameScheduler 调用：阻塞等待直到有帧可取或超时
    // 取出后 frame->owner 变为 OWNED，业务层独占
    VideoFrame* pop(int timeout_ms);

    // 按摄像头 ID 取最新帧（用于定时抓图等非实时场景）
    VideoFrame* peek_latest(int camera_id);

    // 动态调整：增删摄像头时更新内部槽位分配
    void add_camera(int camera_id);
    void remove_camera(int camera_id);

private:
    struct FrameSlot {
        VideoFrame *frame;       // 当前帧（仅保留最新一帧）
        bool        ready;       // 是否有新帧就绪
        pthread_mutex_t lock;
    };
    FrameSlot      *slots_;      // 按 camera_id 索引的槽位数组
    int             max_slots_;
    pthread_mutex_t mutex_;
    pthread_cond_t  cond_;
};
```

调用关系：表示层的 CameraConnectionManager 每采集到一帧就调用 `push()`；业务层的 FrameScheduler 周期性调用 `pop()` 取帧送入 AI 推理管线，TimedCaptureScheduler 调用 `peek_latest()` 获取最新帧用于定时抓拍。

**通道 ② — UpstreamMessageQueue（上行消息队列）**

这是从下层指向上层的通用消息通道，承载两类流向：表示层的协议 I/O 线程将收到的外部消息写入，业务层的 MessageProcessor 消费；数据访问层的 DevicePollingThread 将设备告警事件写入，同样由 MessageProcessor 消费。两条来源的消息统一为 LayerMessage 格式，MessageProcessor 不需要区分消息来自哪一层。

```cpp
class UpstreamMessageQueue {
public:
    explicit UpstreamMessageQueue(int capacity = 1024);
    ~UpstreamMessageQueue();

    // 表示层 / 数据访问层调用：写入一条上行消息
    // 内部拷贝 payload，调用方负责释放原始 payload
    void push(const LayerMessage &msg);

    // 业务层 MessageProcessor 调用：阻塞批量取出
    // 一次最多取 max_count 条，减少锁竞争
    int  pop_batch(LayerMessage *out, int max_count, int timeout_ms);

    // 查询当前积压深度（用于监控和背压告警）
    int  pending_count() const;

private:
    struct Node {
        LayerMessage msg;
        Node        *next;
    };
    Node           *head_;
    Node           *tail_;
    int             count_;
    int             capacity_;
    pthread_mutex_t mutex_;
    pthread_cond_t  not_empty_;
};
```

调用关系：表示层 ProtocolIOThread 收到 MQTT/HTTP 消息后调用 `push()`；数据访问层 DevicePollingThread 检测到设备离线/状态突变时调用 `push()`；业务层 MessageProcessor 在主循环中调用 `pop_batch()` 批量取出后按 `msg.type` 路由分发。

---

**通道 ③ — DownstreamMessageQueue（下行消息队列）**

这是从业务层指向表示层的响应通道。业务层处理完消息后，将需要对外发布的结果（AI 检测上报、异常图片上传、设备状态响应、控制结果、日志上传、模型更新状态等）写入此队列；表示层的 ProtocolIOThread 从队列中取出后，按目标协议分发到 MQTT 客户端或 HTTP 客户端发送出去。

```cpp
class DownstreamMessageQueue {
public:
    explicit DownstreamMessageQueue(int capacity = 1024);
    ~DownstreamMessageQueue();

    // 业务层调用：写入一条下行消息
    void push(const LayerMessage &msg);

    // 表示层 ProtocolIOThread 调用：阻塞批量取出
    int  pop_batch(LayerMessage *out, int max_count, int timeout_ms);

    // 按优先级弹出：严重告警（烟火/摔倒）优先于一般告警（杂物堆放）
    int  pop_batch_priority(LayerMessage *out, int max_count, int timeout_ms);

private:
    // 内部使用优先级小顶堆，MSG_REPORT_ANOMALY 按严重程度排序
    // 其余消息按 FIFO 顺序
    std::priority_queue<PriorityNode> pq_;
    pthread_mutex_t                   mutex_;
    pthread_cond_t                    not_empty_;
};
```

调用关系：业务层 MessageProcessor / AIInferenceEngine / LogManager / RemoteModelUpdater 等模块调用 `push()`；表示层 ProtocolIOThread 在 epoll 循环的每个迭代中调用 `pop_batch_priority()` 取出待发数据，根据消息类型分发到 MQTTClientAdapter（告警/状态上报）或 HTTPClientAdapter（图片/日志/模型文件传输）。

---

**通道 ④ — CommandQueue（命令队列）**

这是业务层向数据访问层下发控制指令的专用通道。设计为"请求-响应"同步模式：业务层写入命令后通过信号量等待结果，数据访问层执行完毕后 signal 通知。写命令优先于读命令执行（控制操作对实时性要求更高），同一总线上的读写通过互斥锁互斥。

```cpp
class CommandQueue {
public:
    explicit CommandQueue(int capacity = 256);
    ~CommandQueue();

    // 业务层 MessageProcessor 调用：
    // 写入命令并阻塞等待结果，超时返回 false
    bool submit(DeviceCommand *cmd);

    // 数据访问层 DevicePollingThread 调用：
    // 非阻塞取出一条命令，无命令时返回 NULL
    DeviceCommand* try_pop();

    // 数据访问层调用：标记命令执行完成（写回 result 并 signal）
    void complete(DeviceCommand *cmd, CmdResult result);

    // 查询等待中的命令数量
    int  pending_count() const;

private:
    struct CmdNode {
        DeviceCommand *cmd;
        CmdNode       *next;
    };
    CmdNode         *head_;
    CmdNode         *tail_;
    int              count_;
    pthread_mutex_t  mutex_;
    pthread_cond_t   not_empty_;
};
```

调用关系：业务层 MessageProcessor 解析出设备控制命令后调用 `submit()`，内部阻塞等待（最多 timeout_ms 毫秒）；数据访问层 DevicePollingThread 在两次设备读取间隙调用 `try_pop()` 取出命令，通过对应的 DeviceDriver 子类执行硬件操作，完成后调用 `complete()` 回写结果并唤醒业务层。

---

**通道 ⑤ — DeviceStatusCache（设备状态缓存）**

这是数据访问层向业务层（以及表示层 UIManager）提供设备状态查询的共享内存区域。数据访问层的轮询线程持续更新缓存，业务层和表示层直接读取，无需等待下一次轮询周期。通过读写锁实现"多读单写"的并发模型——读多写少的场景下性能远优于互斥锁。

```cpp
class DeviceStatusCache {
public:
    DeviceStatusCache();
    ~DeviceStatusCache();

    // 数据访问层 DevicePollingThread 调用：更新某设备状态
    void update(int device_id, const DeviceStatus &status);

    // 数据访问层调用：批量更新（一次轮询周期结束后批量写入）
    void batch_update(const DeviceStatus *statuses, int count);

    // 业务层 / 表示层调用：查询单设备状态（从缓存读，不触发轮询）
    bool get(int device_id, DeviceStatus *out) const;

    // 业务层调用：查询某类型所有设备状态
    int  get_by_type(DeviceType type, DeviceStatus *out, int max_count) const;

    // 业务层调用：查询所有离线设备
    int  get_offline_devices(int *device_ids, int max_count) const;

    // 数据访问层调用：标记设备离线（连续超时超阈值时）
    void mark_offline(int device_id);

private:
    // 按 device_id 索引的哈希表
    std::unordered_map<int, DeviceStatus> cache_;
    pthread_rwlock_t                      rwlock_;  // 读写锁：多读单写
};
```

调用关系：数据访问层 DevicePollingThread 每轮询完一批设备后调用 `batch_update()` 刷新缓存，检测到超时时调用 `mark_offline()`；业务层 MessageProcessor 处理状态查询类消息时调用 `get()` 直接读取最新值返回，无需等待轮询；表示层 UIManager 定期调用 `get_by_type()` 刷新触摸屏上的设备状态显示。

### 三、各层内部实现类

#### 3.1 表示层内部类

```
ProtocolBase (抽象基类)
│  定义所有协议端口的统一接口：init() / start() / stop() / on_readable() / on_writable()
│  子类通过工厂模式由 ProtocolConfigManager 根据 JSON 配置动态创建
│
├── MQTTClientAdapter
│    职责：作为 MQTT 客户端连接物联网云平台
│    内部依赖：MQTT-C 或 Paho Embedded-C 轻量库
│    上行：收到云端指令 → 封装 LayerMessage → push 到 UpstreamMessageQueue
│    下行：从 DownstreamMessageQueue 取出 → 通过 MQTT publish 发送
│    关键方法：
│      on_cloud_message()     收到云端下发消息时回调
│      publish_detection()    发布 AI 检测结果
│      publish_device_event() 发布设备事件
│
├── MQTTServerAdapter
│    职责：作为 MQTT 服务端接收 ESP32/PLC 的传感器数据
│    上行：收到传感器数据 → 封装 LayerMessage → push 到 UpstreamMessageQueue
│    关键方法：
│      on_client_connect()    ESP32 设备接入
│      on_sensor_report()     收到传感器上报数据
│
├── HTTPServerAdapter
│    职责：本地 RESTful API，Token 鉴权

│
└── HTTPClientAdapter
     职责：与物联网平台的 HTTP 交互（文件传输为主）
     下行：从 DownstreamMessageQueue 取出上传任务 → 执行 HTTP 请求
     内部实现：非阻塞 socket + 状态机，支持断点续传和分片上传
     关键方法：
       upload_anomaly_image()  上传异常图片
       upload_capture()       上传定时抓拍图片

#### 3.2 业务层内部类

```

│  职责：从 UpstreamMessageQueue 批量取消息，按 type 路由到对应处理逻辑
│  核心协作（层间交互加粗标注）：
│    ★ 从 UpstreamMessageQueue::pop_batch() 取消息
│    ★ 查询状态时调用 DeviceStatusCache::get() 读取设备缓存
│    ★ 下发控制时调用 CommandQueue::submit() 等待执行结果

│    run()                    主循环：取消息 → 路由 → 处理

│    ★ 从 FrameDispatcher::pop() 取帧
│    ★ 送入 VideoPreprocessor 预处理
│  调度策略：
│    关键摄像头（消防通道/危险区域）优先处理
│    普通摄像头轮转公平调度
│    AI 负载高时自动降低低优先级摄像头频率
│  关键方法：
│    schedule_next_frame()    选取下一帧（优先级 + 时间轮）
│    update_priority()        动态调整摄像头优先级
│    adapt_load()             负载自适应降频

VideoPreprocessor（视频预处理器）
│  职责：利用芯片 RGA 硬件加速执行缩放、色彩空间转换、ROI 裁剪
│  内部依赖：HAL::RGADriver
│    不占用 CPU，输出标准化推理帧放入预处理缓冲队列
│  关键方法：
│    preprocess(frame)        执行 RGA 加速预处理
│    resize_and_convert()     缩放 + NV12→RGB 转换

AIInferenceEngine（AI 推理引擎）
│  职责：调用 NPU 执行目标检测/图像分类
│  内部依赖：HAL::NPUDriver（RKNN 运行时）
│    从预处理缓冲取帧 → 推理 → 结果写入 ResultBuffer
│    异常帧 JPEG 编码后写入 AnomalyImageBuffer
│  核心协作：
│    ★ 推理结果 → ResultBuffer::set() 按摄像头 ID 索引
│    ★ 异常图片 → AnomalyImageBuffer::push() 按严重程度排优先级
│    ★ 检测结果 → DownstreamMessageQueue::push() 通知表示层上报
│  关键方法：
│    infer(frame)             执行单帧推理
│    load_model(path)         加载 RKNN 模型
│    hot_swap_model(new_path) 热切换模型（失败自动回退）
│    on_timeout()             推理超时处理（跳帧继续）

│  职责：根据摄像头配置选择对应的检测模型和任务类型
│  每个摄像头可配置不同策略：
│    烟火检测 / 杂物堆放 / 人员摔倒 → 目标检测模型
│    仪表读数识别 → 图像分类模型
│    开关/挡板/指示灯状态 → 图像分类模型

ResultBuffer（检测结果缓冲）
│  职责：按摄像头 ID 索引，每个摄像头保留最新检测结果
│  查询时直接返回，无需等待新推理
│  附带 CLOCK_MONOTONIC 时间戳保证时间基准一致
│  关键方法：
│    set(camera_id, result)   写入最新结果
│    get(camera_id)           查询最新结果

AnomalyImageBuffer（异常图片缓冲）
│  职责：缓存异常事件的原始帧 JPEG，按优先级排队上传
│  优先级：严重告警（烟火/摔倒）> 一般告警（杂物堆放）
│  网络中断时暂存本地文件系统（按摄像头ID+时间戳命名，上限 1GB）
│  恢复后按优先级补传
│  关键方法：
│    push(frame, severity)    写入异常图片
│    pop_for_upload()         按优先级取出待上传
│    save_to_disk()           网络中断时落盘
│    recover_and_retransmit() 网络恢复后补传

TimedCaptureScheduler（定时抓图调度器）
│  职责：按配置的抓拍间隔从帧分发器获取最新帧，JPEG 编码后存储+上传
│  核心协作：
│    ★ 从 FrameDispatcher::peek_latest() 获取最新帧
│    ★ 上传任务交给 CloudTaskScheduler 统一调度
│  本地存储：按日期/摄像头ID 组织目录，循环覆盖（剩余 < 1GB 时清理最早文件）
│  支持云端远程调整抓拍频率，支持 MQTT 触发即时抓拍

RemoteModelUpdater（远程模型更新模块）
│  职责：接收云端模型更新通知 → 下载 → 校验 → 热切换
│  核心协作：
│    ★ 从 UpstreamMessageQueue 收到 MSG_CLOUD_CMD_MODEL_UPDATE
│    ★ 通过 HTTPClientAdapter 下载模型文件（断点续传）
│    ★ SHA256 校验完整性
│    ★ 通知 AIInferenceEngine::hot_swap_model() 热切换
│    ★ 通过 DownstreamMessageQueue 上报更新状态
│  本地保留当前版本 + 上一版本，支持手动回滚
│  盒子注册时上报芯片型号，服务端据此下发匹配版本

LogManager（日志管理器）
│  职责：分级日志（DEBUG/INFO/WARN/ERROR）+ 本地循环存储 + 增量上传
│  本地：保留最近 7 天或 500MB（先到为准）
│  上传：定时打包压缩 → CloudTaskScheduler 调度上传
│  增量策略：记录上次偏移量，每次只传新增部分
│  ERROR 级别日志不等定时周期，立即通过 MQTT 实时推送
│  支持云端远程调整日志级别、触发即时上传

CloudTaskScheduler（云端任务调度器）
│  职责：统一管理所有与物联网平台的 HTTP 交互任务
│  协调：模型下载 / 日志上传 / 异常图片上传 / 定时抓图上传 / OTA 下载
│  按优先级调度，避免多任务争抢带宽和连接资源
│  关键方法：
│    submit_task(task)        提交上传/下载任务
│    cancel_task(task_id)     取消任务
│    get_bandwidth_usage()    查询当前带宽占用

WatchdogMonitor（看门狗监控线程）
│  职责：每秒检查所有关键线程心跳，超时则尝试重启模块
│  独立于业务层，避免业务层卡死时看门狗同时失效
│  严重时触发硬件看门狗重启整个系统
│  监控目标：UI 线程 / ProtocolIOThread / MessageProcessor /
│            AIInferenceEngine / DevicePollingThread
```

```
DevicePollingThread（设备轮询线程）
│  职责：基于时间轮的非阻塞调度读取设备状态 + 执行控制命令
│  核心协作（层间交互加粗标注）：
│    ★ 轮询结果 → DeviceStatusCache::batch_update() 刷新缓存

│  职责：维护 JSON 格式设备配置表

│  支持热加载：运行时增删设备无需重启
│  关键方法：
│    load_config()            加载配置
│    reload_config()          热加载
│    get_driver(device_id)    按配置创建对应的 DeviceDriver 子类实例

│  定义所有设备驱动的统一接口：read() / write() / get_interface_type()
│
├── GPIODriver         GPIO 数字量读写（门禁、继电器等）
├── ModbusRTUDriver    RS485 Modbus RTU 协议（电表、温湿度变送器等）

│  优先于轮询：硬件支持中断时不走轮询，中断触发后直接更新缓存
│  核心协作：
│    ★ 状态变化 → DeviceStatusCache::update() 立即刷新

│  职责：封装芯片级硬件差异，对上提供统一接口

├── NPUDriver

│    RK3576：6TOPS，INT8/FP16，单帧 20~25ms

│    RK3576：4K@120fps
│    RK3588：8K@30fps / 4K@120fps
│
└── RGADriver

### 五、线程归属与层间交互类的并发安全

六个线程各自操作的层间交互类汇总如下，这也是理解并发安全的关键。

```
线程                    所属层      操作的层间交互类
───────────────────    ────────    ──────────────────────────────────
UI 线程                表示层      DeviceStatusCache (读)
                                   DownstreamMessageQueue (读)

ProtocolIOThread       表示层      UpstreamMessageQueue (写)
                                   DownstreamMessageQueue (读)
                                   FrameDispatcher (写: push)

MessageProcessor       业务层      UpstreamMessageQueue (读)
                                   DownstreamMessageQueue (写)
                                   CommandQueue (写: submit)
                                   DeviceStatusCache (读)
                                   FrameScheduler (调度)

AIInferenceEngine      业务层      FrameDispatcher (读: pop)
                                   ResultBuffer (写)
                                   AnomalyImageBuffer (写)
                                   DownstreamMessageQueue (写)

WatchdogMonitor        业务层      不直接操作层间队列，仅监控线程心跳

DevicePollingThread    数据访问层  DeviceStatusCache (写)
                                   CommandQueue (读: try_pop, 写: complete)
                                   UpstreamMessageQueue (写: 设备告警)
```

并发安全保证措施：所有层间交互类内部均使用 pthread_mutex + pthread_cond（或 pthread_rwlock）保护共享状态。FrameDispatcher 和 CommandQueue 使用互斥锁 + 条件变量实现阻塞等待；DeviceStatusCache 使用读写锁实现多读单写；UpstreamMessageQueue 和 DownstreamMessageQueue 使用互斥锁 + 条件变量实现生产者-消费者模型。所有队列均设置容量上限，满时通过丢弃策略（帧队列丢旧帧、消息队列阻塞生产者）防止内存溢出。
