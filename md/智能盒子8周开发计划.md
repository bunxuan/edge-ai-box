## 智能盒子 8 周开发计划

> **适用对象**：具有较好算法与 C/C++ 基础，但嵌入式 Linux 开发经验较少的开发者。
> **硬件平台**：瑞芯微 RK3568 开发板（后续可平滑升级 RK3576/RK3588）。
> **开发目标**：完成智能盒子三层架构全部功能模块的开发、联调与验收。

---

### 总体节奏

```
第1周 ─── 环境搭建 + HAL 层 + 数据访问层基础
第2周 ─── 数据访问层完善 + 层间通道实现
第3周 ─── 表示层：协议适配（MQTT + HTTP）
第4周 ─── 表示层：摄像头连接管理 + 帧采集
第5周 ─── 业务层：消息处理 + 帧调度 + 预处理
第6周 ─── 业务层：AI 推理管线
第7周 ─── 业务层：辅助模块（抓图/模型更新/日志/云端调度）
第8周 ─── 系统集成 + 看门狗 + OTA + 联调验收
```

每周按 **5 个工作日** 规划，每天有效开发时间按 6~8 小时计。每周末设有明确的 **检查成果**，用于验收当周进度是否达标。

### 第 1 周：开发环境搭建 + HAL 层 + 数据访问层基础

#### 开发任务

**Day 1~2：交叉编译环境与开发板调试**

在宿主机（Ubuntu 20.04/22.04 x86_64）上搭建 RK3568 交叉编译工具链。安装 aarch64 交叉编译器（gcc-linaro 或 Buildroot 工具链），配置 CMake 交叉编译工具链文件（toolchain.cmake），完成一个 hello world 程序的交叉编译并部署到开发板运行。通过 ADB 或 SSH 连接开发板，熟悉板子的文件系统布局、串口调试方法。

技术说明：交叉编译是嵌入式开发的第一步，也是初学者最容易卡住的环节。RK3568 是 ARM64（AArch64）架构，必须使用 aarch64 开头的工具链。CMake 的交叉编译配置文件需要指定 CMAKE_SYSTEM_NAME=Linux、CMAKE_SYSTEM_PROCESSOR=aarch64、以及编译器的完整路径。建议将工具链路径写入环境变量，避免硬编码。

**Day 3：RKNN 工具链与 NPU 基础**

在宿主机上安装 RKNN Toolkit2（Python 版），这是将训练好的模型转换为 RKNN 格式的工具。用官方提供的 YOLOv5s 预训练模型做一次完整的"ONNX → RKNN → 板端推理"流程验证。在开发板上运行 RKNN 官方示例程序（rknn_api_demo），确认 NPU 驱动正常工作，单帧推理耗时在 55~65ms 范围内。

技术说明：RKNN Toolkit2 运行在 x86 宿主机上，负责模型转换和量化（INT8/FP16）；RKNN Runtime 运行在 ARM 开发板上，负责加载 .rknn 模型并调用 NPU 推理。两者版本必须严格对应。量化方式直接影响推理精度和速度，RK3568 的 1TOPS NPU 建议使用 INT8 动态量化。

**Day 4~5：HAL 层接口设计与实现**

根据架构设计文档中的 HardwareAbstractionLayer 门面类定义，实现 HAL 层的三个核心驱动接口：NPUDriver（封装 RKNN Runtime C API）、RGADriver（封装 librga 图形加速库）、VideoDecoderDriver（封装 MPP 媒体处理平台库）。每个驱动实现统一的 C 接口（函数指针表），上层代码通过 HAL 门面类调用，不直接依赖具体芯片 API。编写单元测试，在开发板上验证 HAL 接口可正常调用 NPU 推理、RGA 缩放、视频解码功能。

技术说明：HAL 层是三层架构与硬件解耦的关键。RK3568 上有三个关键硬件模块需要封装：NPU 通过 RKNN Runtime C API 调用（头文件 rknn_api.h，核心函数 rknn_init/rknn_run/rknn_destroy）；RGA 通过 librga 库调用（头文件 im_rga.h，核心函数 imcheck/imcopy/imresize 等，可硬件加速缩放和色彩空间转换，不占 CPU）；视频解码通过 MPP（Media Process Platform）库调用（核心函数 mpi_dec_test 系列，支持 H.265/H.264 硬解码）。封装时注意将这三个库的头文件和 .so 动态库单独整理到一个 sysroot 目录，CMake 中通过 find_package 或 pkg-config 引用。

### 第 2 周：数据访问层完善 + 层间通道实现

#### 开发任务

**Day 1~2：设备驱动实现**

实现四个 DeviceDriver 子类：GPIODriver（读写 GPIO 引脚，控制门禁继电器）、ModbusRTUDriver（通过 RS485 串口与 Modbus 设备通信，读取电表/温湿度变送器数据）、I2CDriver（读取 I2C 温湿度传感器）、SPIDriver（预留接口）。每个驱动实现 DeviceDriver 基类的 read()/write() 接口。在开发板上用实际硬件（或模拟设备）验证各驱动的读写功能。

技术说明：GPIO 在 Linux 下通过 /dev/gpiochipN 字符设备操作（使用 libgpiod 库），不建议直接操作 /sys/class/gpio  sysfs 接口（已标记 deprecated）。Modbus RTU 通过 /dev/ttySx 串口设备操作，推荐使用 libmodbus 开源库（封装了 RTU/TCP 协议细节，开发者只需调用 modbus_read_registers 等高层接口）。I2C 通过 /dev/i2c-N 设备操作，使用 i2c-tools 库或直接用 ioctl(I2C_RDWR)。SPI 通过 /dev/spidevN.M 操作。初学者注意：同一总线上的读写必须加互斥锁，否则会出现数据错乱。

**Day 3：DevicePollingThread 与 DeviceConfigManager**

实现设备配置管理器（读取 JSON 设备配置表）和设备轮询线程。轮询线程基于时间轮的非阻塞调度：每个设备维护一个 next_poll_time，主循环每次遍历检查是否有设备到达轮询时刻，到达则调用对应驱动的 read() 方法，未到达则跳过。通信超时处理：记录连续超时计数，超过阈值调用 DeviceStatusCache::mark_offline() 并上报告警。两次读取间隙检查 CommandQueue，写命令优先执行。

技术说明：时间轮调度的核心思想是避免"固定间隔轮询所有设备"的低效模式。假设温湿度传感器每 5 秒读一次、电表每 30 秒读一次、门禁用中断驱动不轮询——时间轮让每个设备按自己的频率独立调度，互不干扰。非阻塞的关键是每次 read() 调用设置超时（如串口设置 VMIN=0, VTIME=50 即 5 秒超时），超时后立即返回不卡住整个线程。

**Day 4：DeviceStatusCache + CommandQueue + UpstreamMessageQueue**

实现三个层间交互类。DeviceStatusCache 内部用哈希表 + 读写锁（pthread_rwlock）实现多读单写。CommandQueue 内部用链表 + 互斥锁 + 条件变量实现，submit() 写入命令后通过信号量（sem_t）阻塞等待结果。UpstreamMessageQueue 内部用链表 + 互斥锁 + 条件变量实现生产者-消费者模型。编写多线程测试程序验证：一个线程写、另一个线程读，检查并发安全性和数据完整性。

技术说明：这三个类是层间通信的基础设施，并发安全至关重要。读写锁（pthread_rwlock）适用于"读多写少"场景——DeviceStatusCache 被业务层频繁读取，但只有轮询线程写入，读写锁允许多个读者同时进入，写者独占。条件变量（pthread_cond_t）配合互斥锁使用，注意必须用 while 循环检查条件（而非 if），防止虚假唤醒（spurious wakeup）。信号量（sem_t）用于 CommandQueue 的"请求-响应"同步模式，比互斥锁+条件变量更简洁。

**Day 5：DownstreamMessageQueue + FrameDispatcher + 联调**

实现剩余两个层间交互类。DownstreamMessageQueue 在普通消息队列基础上加入优先级排序（std::priority_queue），严重告警消息优先弹出。FrameDispatcher 实现按摄像头 ID 索引的帧槽位数组，push() 时新帧覆盖旧帧，pop() 阻塞等待。编写集成测试：模拟表示层写入帧和消息，验证业务层能正确取出。

技术说明：FrameDispatcher 的"所有权转移"是性能关键设计。视频帧数据量大（一帧 640×640×1.5 字节 ≈ 600KB），如果每次传递都拷贝一份，16 路摄像头每 10 秒一帧的拷贝开销约 9.6MB/s，对嵌入式设备的内存带宽是不小的负担。所有权转移意味着 push 后原指针失效，pop 后消费者独占，全程零拷贝。实现时用 FrameOwner 枚举标记所有权状态，调试时可通过断言检查所有权一致性。

### 第 3 周：表示层——协议适配（MQTT + HTTP）

#### 开发任务

**Day 1~2：MQTT 协议适配**

集成 MQTT-C 或 Eclipse Paho Embedded-C 轻量库。实现 MQTTClientAdapter：连接物联网云平台（配置 broker 地址、端口、TLS 证书、用户名密码认证），实现 connect/publish/subscribe 三个核心操作。订阅主题包括：模型更新通知、抓图频率调整、日志级别切换、即时抓拍请求、摄像头增删配置等管理指令。收到消息后封装为 LayerMessage 写入 UpstreamMessageQueue。实现 MQTTServerAdapter：启动本地 MQTT broker 功能（或使用 mosquitto 嵌入式版），接收各 ESP32/PLC 客户端连接，解析传感器上报数据后封装为 LayerMessage 写入 UpstreamMessageQueue。

技术说明：MQTT 协议是物联网的标准通信协议，核心概念包括：Broker（消息服务器）、Topic（主题，层级结构如 /device/sensor/temp）、QoS（服务质量等级，0=最多一次/1=至少一次/2=恰好一次）。智能盒子作为 MQTT Client 连接云端 Broker 时用 QoS 1（保证指令不丢失），作为 MQTT Server 接收 ESP32 数据时用 QoS 0（传感器数据频率高，允许偶尔丢失）。TLS 加密连接在嵌入式设备上推荐使用 mbedTLS 库（比 OpenSSL 轻量得多，内存占用约 60KB vs 500KB+）。MQTT-C 是纯 C 实现的轻量 MQTT 客户端（约 2000 行代码），适合资源受限的嵌入式环境；Paho Embedded-C 是 Eclipse 基金会的官方嵌入式版本，功能更完整但体积更大。

**Day 3~4：HTTP 协议适配**

实现 HTTPServerAdapter：基于轻量 HTTP 库（推荐 Mongoose 或 libmicrohttpd）提供本地 RESTful API。接口包括 GET /api/devices（查询所有设备状态）、GET /api/devices/{id}（查询单设备）、POST /api/devices/{id}/control（下发控制命令）、GET /api/cameras（查询摄像头列表）、POST /api/cameras（增删摄像头配置）。使用 Token 鉴权中间件防止未授权访问。收到请求后封装为 LayerMessage 写入 UpstreamMessageQueue，从 DownstreamMessageQueue 取出响应数据返回给客户端。

实现 HTTPClientAdapter：基于非阻塞 socket + 状态机实现与物联网平台的 HTTP 交互。状态机包含 IDLE → CONNECTING → SENDING → RECEIVING → DONE 五个状态，每个状态在 epoll 可写/可读时推进一步，避免任何阻塞调用。支持断点续传（HTTP Range 头）和分片上传（multipart/form-data）。

技术说明：HTTPClientAdapter 的状态机设计是嵌入式网络编程的关键模式。传统阻塞式 HTTP 请求（如 libcurl 的默认模式）在网络延迟时会阻塞整个线程，而嵌入式设备的线程资源极其宝贵。状态机模式将一次 HTTP 请求拆分为多个非阻塞步骤，每步只在 socket 可写/可读时执行一小段，其余时间让出 CPU。Mongoose 是一个单文件（mongoose.h + mongoose.c 共约 7000 行）的嵌入式 Web 服务器/客户端库，同时支持 HTTP 和 MQTT，非常适合本项目。

**Day 5：ProtocolConfigManager + ProtocolIOThread 框架**

实现 ProtocolConfigManager：读取 JSON 配置文件中的协议参数（MQTT broker 地址/端口/认证信息、HTTP 端口/Token、各协议开关等），通过工厂模式根据配置动态创建协议实例。实现 ProtocolIOThread 骨架：基于 epoll 的 I/O 多路复用主循环，将 MQTT Client/Server、HTTP Server/Client 的文件描述符统一注册到 epoll 实例，在单次循环中统一调度所有协议的读写事件。收到数据后写入 UpstreamMessageQueue，从 DownstreamMessageQueue 取出待发数据写入对应 socket。

技术说明：epoll 是 Linux 下最高效的 I/O 多路复用机制（比 select/poll 好在不需要遍历整个文件描述符集合），核心 API 只有三个：epoll_create 创建实例、epoll_ctl 注册/修改/删除监听事件、epoll_wait 阻塞等待事件就绪。一个 ProtocolIOThread 管理所有网络协议的关键优势是：单线程内无锁调度，避免了多线程网络模型中复杂的锁竞争问题。所有 socket 都设置为非阻塞模式（O_NONBLOCK），读写时如果 EAGAIN/EWOULDBLOCK 则立即返回，等下次 epoll 通知再处理。

### 第 4 周：表示层——摄像头连接管理 + 帧采集

#### 开发任务

**Day 1~2：CameraConnectionManager + CameraInstance**

实现摄像头连接管理器。启动时读取 JSON 摄像头配置文件（每路摄像头的 ID、名称、RTSP 地址/ONVIF 快照地址、分辨率、抽帧间隔、是否启用 AI 检测、检测业务类型），批量创建 CameraInstance 实例。实现动态增删摄像头的接口：收到 MQTT 云端指令或 HTTP 本地请求后，管理器调用 add_camera()/remove_camera() 建立或断开连接，同时通知 FrameDispatcher 分配或释放帧槽位。

技术说明：JSON 摄像头配置文件的结构设计很关键，建议格式如下：每路摄像头一个对象，包含 id（整数）、name（字符串）、protocol（"onvif" 或 "rtsp"）、url（RTSP 地址或 ONVIF 快照 URL）、width/height（分辨率）、frame_interval（抽帧间隔秒数）、enable_ai（布尔值）、detection_type（"fire_smoke"/"debris"/"fall_person"/"meter_reading"/"switch_status" 等）。管理器启动时用 cJSON 解析配置，为每路摄像头创建一个 CameraInstance 并注册到 FrameDispatcher。

**Day 3：OnvifSnapshotFetcher**

实现 ONVIF 快照拉取器。通过 HTTP GET 请求 ONVIF 兼容摄像头的快照接口（典型 URL 如 http://camera-ip/onvif-http/snapshot），直接获取单帧 JPEG 图像。实现 Digest 认证（ONVIF 摄像头通常需要用户名密码认证）。拉取到的 JPEG 数据解码为原始像素格式后封装为 VideoFrame，写入 FrameDispatcher。

技术说明：ONVIF 快照方式是本系统的首选采集方案，优势在于不需要维持持续的 RTSP 流连接，每次按需拉取单帧 JPEG，网络带宽和内存占用极低。实现上就是一个简单的 HTTP GET 请求，但需要注意：部分摄像头的 ONVIF 快照接口需要 Digest 认证（比 Basic 认证安全，密码不以明文传输），可使用 libcurl 的 CURLOPT_HTTPAUTH=CURLAUTH_DIGEST 自动处理。拉取频率由 frame_interval 配置控制（如每 10 秒拉一次），用定时器触发。如果摄像头不支持 ONVIF，自动回退到 RTSP 方式。

**Day 4：RtspStreamDecoder**

实现 RTSP 流解码器（ONVIF 不可用时的回退方案）。使用 FFmpeg 的 libavformat/libavcodec 库（或更轻量的 live555 库）建立 RTSP 连接，将 H.265/H.264 码流送入 HAL::VideoDecoderDriver 进行硬件解码，解码后的原始帧按配置间隔抽取，封装为 VideoFrame 写入 FrameDispatcher。

技术说明：RTSP 方式比 ONVIF 快照复杂得多——需要维持持续的 TCP 连接、处理 RTP 包重组、应对网络抖动和断线重连。硬件解码是关键：RK3568 的 MPP 库支持 H.265/H.264 4K@60fps 硬解码，解码过程不占 CPU。使用 MPP 解码的流程是：创建 MppContext → 送入码流数据（MPP_PACKET）→ 取出解码帧（MPP_FRAME）→ 得到 NV12 格式的原始图像。注意 RTSP 断线重连逻辑：检测到连接断开后等待 2 秒重试，最多重试 5 次，全部失败后标记该摄像头离线并上报。

**Day 5：ProtocolIOThread 集成 + 联调**

将摄像头采集集成到 ProtocolIOThread 的 epoll 循环中。ONVIF 快照的 HTTP 连接和 RTSP 的 socket 都注册到同一个 epoll 实例，与 MQTT/HTTP 协议共享同一个 I/O 线程。验证 16 路摄像头（模拟源）同时采集时，FrameDispatcher 能正确接收和分发帧数据。

技术说明：将摄像头采集纳入 epoll 循环后，单线程需要同时处理大量并发连接（16 路 RTSP + MQTT + HTTP），这对 epoll 的事件处理效率提出了要求。关键优化点：ONVIF 快照是短连接（HTTP GET 完即断），RTSP 是长连接，两者在 epoll 中的事件处理逻辑不同。建议将 ONVIF 请求做成"请求队列 + 并发限制"模式（同一时刻最多 N 个 ONVIF 请求在途），避免瞬间发起 16 个 HTTP 请求导致摄像头端过载。

### 第 5 周：业务层——消息处理 + 帧调度 + 预处理

#### 开发任务

**Day 1~2：MessageProcessor 消息处理线程**

实现业务层的路由中枢。主循环从 UpstreamMessageQueue::pop_batch() 批量取出消息，按 LayerMessage.type 字段路由到对应处理函数。路由表包括：MSG_SENSOR_DATA → handle_sensor_data()（处理 ESP32/PLC 传感器数据）；MSG_CLOUD_CMD_* → handle_cloud_command()（分发到 TimedCaptureScheduler/RemoteModelUpdater/LogManager 等子模块）；MSG_LOCAL_CONTROL → handle_control_command()（校验权限后写入 CommandQueue）；MSG_DEVICE_EVENT → handle_device_event()（设备离线/状态突变处理）。

对于状态查询类消息，直接从 DeviceStatusCache 和 ResultBuffer 读取最新值返回，不等待新推理。对于控制命令，调用 CommandQueue::submit() 并设置超时等待，超时返回失败。

技术说明：MessageProcessor 是业务层唯一的"入口"线程，所有来自表示层和数据访问层的消息都经过它路由分发。设计要点是"快速路由、不阻塞"——每个消息的处理逻辑应该尽量简短，耗时操作（如模型下载、日志上传）应交给专门的模块异步执行，MessageProcessor 只负责触发。消息路由表建议用函数指针数组实现（以 MsgType 枚举值为索引），比 if-else/switch 链更高效且易于扩展。

**Day 3：FrameScheduler 帧调度器**

实现帧调度器。从 FrameDispatcher::pop() 获取就绪帧，根据各摄像头配置的优先级和抽帧间隔决定处理顺序。关键摄像头（消防通道、危险区域）的帧优先处理；普通摄像头按轮转（Round-Robin）方式公平调度。当 AI 推理负载较高时（通过监测预处理队列深度判断），自动降低低优先级摄像头的处理频率（如从 10 秒一次降为 20 秒一次），保证关键摄像头的检测时效性。

技术说明：调度器的核心是一个优先级队列 + 时间窗口的组合。每路摄像头维护一个 next_process_time（下次应处理时间），调度器每次从所有就绪的摄像头中选优先级最高的取帧。优先级相同时按"最久未处理"排序（保证公平性）。自适应降频的实现：当预处理队列中积压帧数超过阈值（如 8 帧），将低优先级摄像头的 frame_interval 临时翻倍。这个阈值和倍率应设计为可配置参数。

**Day 4：VideoPreprocessor 视频预处理**

实现视频预处理模块。从 FrameScheduler 获取原始帧后，调用 HAL::RGADriver 执行硬件加速的缩放（统一到模型输入尺寸，如 640×640）、色彩空间转换（NV12 → RGB）、ROI 裁剪（如果配置了感兴趣区域）。预处理后的帧放入预处理缓冲队列，等待 AI 推理线程取用。

技术说明：RGA 是瑞芯微芯片内置的 2D 图形加速引擎，可以硬件完成图像缩放、旋转、色彩空间转换、裁剪等操作，完全不占 CPU。这对于嵌入式设备至关重要——如果用 CPU 做 640×640 的 NV12→RGB 转换，每帧约需 2~3ms，16 路摄像头就是 32~48ms，而 RGA 只需 0.1~0.3ms/帧。调用流程：rga_create → rga_set_src/dst → rga_set_rect（设置 ROI）→ rgo_blit（触发硬件加速）→ rga_destroy。注意 RGA 对输入格式有要求（支持 NV12/NV21/RGB/ARGB 等），需要与解码输出格式匹配。

**Day 5：层间通道联调 + 端到端数据流验证**

将表示层（帧采集 + 协议）与业务层（消息处理 + 帧调度 + 预处理）联调。验证完整的数据流：摄像头采集帧 → FrameDispatcher → FrameScheduler → VideoPreprocessor → 预处理缓冲队列。同时验证消息流：MQTT 收到云端指令 → UpstreamMessageQueue → MessageProcessor 路由 → CommandQueue → DevicePollingThread 执行 → DownstreamMessageQueue → MQTT 返回结果。用模拟数据源（如本地视频文件循环播放代替真实摄像头）进行全链路测试。

技术说明：联调阶段最容易暴露的问题是时序问题和内存问题。时序问题的典型表现是"偶尔取到空帧"或"帧顺序错乱"——原因通常是 FrameDispatcher 的锁粒度不对，或者所有权转移的时机有误。内存问题的典型表现是"运行几小时后内存持续增长"——原因通常是帧数据没有正确释放（所有权转移后原指针未置空，导致 double free 保护跳过了释放）。建议使用 valgrind 的 massif 工具监控内存峰值，使用 AddressSanitizer（编译时加 -fsanitize=address）检测内存越界和泄漏。

### 第 6 周：业务层——AI 推理管线

#### 开发任务

**Day 1~2：AIInferenceEngine 核心推理**

实现 AI 推理引擎。从预处理缓冲队列取帧，调用 HAL::NPUDriver 执行 RKNN 推理。推理结果封装为 DetectionResult（摄像头 ID、目标类别、置信度、边界框坐标），写入 ResultBuffer（按摄像头 ID 索引，每个摄像头保留最新结果）。每条结果附带 CLOCK_MONOTONIC 时间戳。实现推理超时处理：如果单次推理超过 500ms，自动跳过当前帧继续处理下一帧，防止管线堵塞。

技术说明：RKNN 推理的完整流程是：rknn_init(加载模型) → rknn_inputs_set(设置输入张量) → rknn_run(触发 NPU 推理) → rknn_outputs_get(取出输出张量) → 后处理（NMS 非极大值抑制、置信度过滤等）。后处理是目标检测的关键步骤——YOLOv5 的输出是数千个候选框，需要通过 NMS 去除重叠框、通过置信度阈值过滤低质量检测。NMS 的实现建议直接用 CPU（计算量不大，约 1~2ms），不需要放到 NPU 上。推理超时保护很重要：如果 NPU 偶尔出现异常导致推理卡住，超时机制保证管线不会整体堵塞。

**Day 3：InferenceStrategy + 多模型管理**

实现推理策略模块。不同摄像头可配置不同的检测任务（烟火检测、杂物堆放、人员摔倒用目标检测模型；仪表读数识别、开关/挡板/指示灯状态用图像分类模型），InferenceStrategy 根据摄像头 ID 查询配置，选择对应的模型和检测参数。支持按摄像头分组加载不同模型（如 A 组用烟火检测模型，B 组用仪表读数模型）。

技术说明：多模型管理的内存开销需要关注。每个 RKNN 模型加载后会占用 NPU 内存（通常几 MB 到几十 MB），RK3568 最大 8GB 系统内存，NPU 可用内存约 200~300MB。如果同时加载 5 个不同模型，每个约 20MB，总共约 100MB，在可接受范围内。但如果模型数量更多，需要考虑"按需加载"策略——只在推理时加载对应模型，推理完释放。不过这种方式的模型加载延迟（约 200~500ms）会影响实时性，建议优先尝试全部常驻内存。

**Day 4：ResultBuffer + AnomalyImageBuffer**

实现结果缓冲和异常图片缓冲。ResultBuffer 按摄像头 ID 索引的哈希表，每个摄像头保留最新检测结果，查询时直接返回。AnomalyImageBuffer 接收 AI 推理线程判定的异常帧，JPEG 编码后按严重程度排入优先级队列（烟火/摔倒 > 杂物堆放）。网络中断时异常图片暂存本地文件系统（按摄像头 ID 和时间戳命名，存储上限 1GB），恢复后按优先级补传。

技术说明：异常图片的 JPEG 编码可以在 AI 推理线程中完成（使用 libjpeg-turbo 库，编码速度约 2~5ms/帧），也可以交给独立的编码线程。如果异常事件频繁发生（如持续检测到烟火），编码可能成为瓶颈——建议加入"去重"逻辑：同一摄像头在 N 秒内只保留第一张异常图片（如 30 秒内同一摄像头的烟火告警只保存首张），避免存储和网络带宽被同一事件的大量重复图片占满。

**Day 5：AI 推理性能调优**

对 AI 推理管线进行性能测试和调优。测试不同摄像头数量（1/4/8/12/16 路）下的推理吞吐和延迟。调整 FrameScheduler 的优先级参数和自适应降频阈值，观察对关键摄像头检测时效性的影响。测试推理超时机制在 NPU 异常时的保护效果。

技术说明：性能调优的核心指标是"单路摄像头的检测延迟"——从帧采集到推理结果输出的总时间。理想情况下，10 秒抽帧间隔 + 55~65ms 推理 + 5ms 预处理 ≈ 总延迟 60~70ms，完全满足监控场景需求。但如果 16 路摄像头同时就绪，调度器需要 16 × 65ms ≈ 1040ms 才能处理完一轮，这意味着最后一路摄像头的有效检测间隔约 11 秒（比配置的 10 秒略长），属于可接受范围。如果摄像头数量进一步增加，就需要启用自适应降频或升级到 RK3576/RK3588。

### 第 7 周：业务层——辅助模块

#### 开发任务

**Day 1：TimedCaptureScheduler 定时抓图**

实现定时抓图调度器。为每路摄像头独立配置抓拍时间间隔（支持固定间隔如每 5 分钟、每小时，或自定义 cron 表达式）。到期时从 FrameDispatcher::peek_latest() 获取该摄像头最新帧，JPEG 编码后存入本地抓拍目录（按日期/摄像头 ID 组织子目录，文件名含摄像头 ID 和时间戳），同时通过 CloudTaskScheduler 上传至物联网平台。本地存储采用循环覆盖策略：当剩余空间低于 1GB 时按摄像头均匀清理最早的文件。支持云端远程调整抓拍频率，支持 MQTT 触发即时抓拍。

技术说明：cron 表达式的解析可以使用轻量级库如 croncpp（纯 C++ 头文件库，约 200 行代码），或者自行实现一个简化版（只支持"分 时 日 月 周"五个字段）。定时器的实现建议使用 timerfd_create（Linux 定时器文件描述符），可以注册到 epoll 中统一调度，不需要额外线程。抓图与 AI 推理独立运行、互不干扰——抓图从 FrameDispatcher 取帧，AI 推理从 FrameScheduler 取帧，两者通过 FrameDispatcher 的内部锁保证并发安全。

**Day 2：RemoteModelUpdater 远程模型更新**

实现远程模型更新的完整流程。收到 MQTT 模型更新通知后，通过 HTTPClientAdapter 下载新模型文件（RKNN 格式），下载过程使用分片传输和断点续传（HTTP Range 头）。下载完成后 SHA256 哈希校验文件完整性。校验通过后将新模型写入备用存储区域，通过 MQTT 上报下载完成确认。通知 AIInferenceEngine 在下一个推理周期加载新模型并释放旧模型内存，实现无缝热切换。加载失败时自动回退到旧模型，并通过 MQTT 上报失败原因。

技术说明：模型热切换的"无缝"是关键——切换过程中不能丢失推理帧。实现思路是"双缓冲"：AIInferenceEngine 同时持有当前模型和新模型的 RKNN context，切换时先在后台加载新模型（rknn_init），加载成功后将推理输入切换到新模型，最后释放旧模型（rknn_destroy）。如果新模型加载失败，推理输入不切换，继续使用旧模型。本地保留两个版本（current + previous），支持手动回滚到上一版本。SHA256 校验使用 OpenSSL 的 EVP_Digest 系列函数或更轻量的 mbedTLS sha256 函数。

**Day 3：LogManager 日志系统**

实现分级日志系统。日志级别：DEBUG / INFO / WARN / ERROR。每条日志包含时间戳、模块名、摄像头 ID（如适用）、日志级别和消息内容。本地以循环文件方式存储（保留最近 7 天或 500MB，先到为准）。日志提交由定时触发（默认每 10 分钟一次，服务端可远程调整），将本地日志打包压缩（gzip）后通过 CloudTaskScheduler 上传。上传采用增量策略：记录上次成功上传的日志偏移量，每次只上传新增部分。ERROR 级别日志不等定时周期，产生后立即通过 MQTT 实时推送。

技术说明：嵌入式设备的日志系统需要注意两点。第一，日志写入不能阻塞业务线程——建议 LogManager 内部维护一个无锁环形缓冲（lock-free ring buffer），业务线程只需将日志消息写入缓冲即返回，由 LogManager 的后台定时器负责批量刷盘。第二，循环文件的清理策略要简单可靠——按文件创建时间排序，超过保留期限的直接删除（而非截断），避免文件碎片。日志打包上传使用 zlib 的 gzip 接口，压缩比通常可达 5:1 ~ 10:1。

**Day 4：CloudTaskScheduler 云端任务调度器**

实现统一的云端任务调度器。所有与物联网平台的 HTTP 交互任务（模型下载、日志上传、异常图片上传、定时抓图上传、OTA 固件下载）都提交到 CloudTaskScheduler 的任务队列中，由调度器按优先级统一调度执行。避免多个上传下载任务同时争抢网络带宽和 HTTP 连接资源。

技术说明：CloudTaskScheduler 本质上是一个优先级任务队列 + 单线程消费者。任务类型包括 UPLOAD_ANOMALY（最高优先级）、UPLOAD_CAPTURE、UPLOAD_LOG、DOWNLOAD_MODEL、DOWNLOAD_OTA。调度器同一时刻只执行一个任务（串行执行），避免并发 HTTP 请求导致的带宽争抢。如果网络带宽有余量（通过测量实际吞吐量判断），可以允许 2 个任务并行（如一个上传 + 一个下载，方向不同不冲突）。任务失败时自动重试（最多 3 次，指数退避间隔 5s/15s/45s）。

**Day 5：辅助模块联调**

将四个辅助模块与消息处理线程、层间通道联调。验证完整流程：MQTT 收到抓图频率调整指令 → MessageProcessor 分发到 TimedCaptureScheduler → 调整抓拍间隔 → 下次抓拍按新间隔执行。MQTT 收到模型更新通知 → RemoteModelUpdater 下载 → 校验 → 热切换 → 上报状态。ERROR 日志产生 → LogManager 立即通过 MQTT 推送。异常图片产生 → AnomalyImageBuffer → CloudTaskScheduler 调度上传。

### 第 8 周：系统集成 + 看门狗 + OTA + 联调验收

#### 开发任务

**Day 1：WatchdogMonitor 看门狗**

实现看门狗监控线程。各关键线程（UI 线程、ProtocolIOThread、MessageProcessor、AIInferenceEngine、DevicePollingThread）各自周期性更新心跳标记（建议每 500ms 更新一次）。看门狗线程每秒检查所有心跳，任一线程超过 3 秒未更新则记录 WARN 日志并尝试重启对应模块。如果重启后 10 秒内仍未恢复，触发硬件看门狗重启整个系统（通过 /dev/watchdog 字符设备）。

技术说明：看门狗的设计原则是"独立于被监控对象"。如果看门狗和业务线程在同一个进程内、共享同一个事件循环，那么进程卡死时看门狗也会同时失效。本系统的看门狗是独立线程，与各业务线程通过共享内存（心跳标记数组）通信。硬件看门狗是最后一道防线——Linux 内核的 /dev/watchdog 设备需要定期"喂狗"（写入任意字符），如果应用层卡死导致无法喂狗，硬件看门狗会在超时后自动复位系统。注意：打开 /dev/watchdog 后内核会启动计时器，关闭时计时器停止，所以一旦启用就不能意外关闭。

**Day 2：OTA 双分区升级**

实现 OTA（Over-The-Air）双分区 A/B 升级机制。系统固件分为 A/B 两个分区，当前从 A 分区启动时，OTA 固件下载到 B 分区，写入完成后修改 bootloader 启动标记，重启后从 B 分区启动。如果新固件启动后 30 秒内未正常完成初始化（看门狗判定启动失败），自动回滚到 A 分区重启。OTA 固件按芯片型号分别编译和签名，盒子在下载前校验固件签名和芯片型号匹配性，防止错误固件刷入。

技术说明：A/B 双分区是嵌入式设备 OTA 升级的标准方案，核心思想是"永远保留一个可启动的分区"。即使新固件写入失败或损坏，旧分区仍然可以正常启动。实现要点：bootloader（如 U-Boot）需要支持环境变量标记当前启动分区（boot_partition=A/B），OTA 完成后修改环境变量并重启。签名校验使用 RSA-2048 或 Ed25519，防止固件被篡改。固件包格式建议为：魔数(4B) + 版本号(16B) + 芯片型号(16B) + 固件大小(4B) + SHA256(32B) + 签名(256B) + 固件数据。

**Day 3~4：全系统集成联调**

将三层架构所有模块集成到一起，在 RK3568 开发板上进行全系统联调。按以下顺序验证：

（1）启动顺序验证：HAL 初始化 → 数据访问层启动（设备轮询开始）→ 表示层启动（协议连接建立、摄像头连接初始化）→ 业务层启动（消息处理、AI 推理、辅助模块就绪）。

（2）核心业务流程验证：多路摄像头采集 → AI 推理检测 → 结果上报云端 → 异常图片上传 → 云端下发控制命令 → 设备执行 → 结果返回。

（3）异常场景验证：网络断开后恢复（日志补传、图片补传）、NPU 推理超时（自动跳帧）、设备通信超时（标记离线）、模型更新失败（自动回退）。

（4）长时间稳定性测试：全功能运行 48 小时，监控内存占用、CPU 使用率、推理延迟、网络吞吐量。

技术说明：集成联调阶段最常见的问题是启动顺序依赖和线程初始化时序。例如，MessageProcessor 启动后如果 UpstreamMessageQueue 还没有被表示层写入任何消息，pop_batch 会阻塞等待——这是正常的，但需要确保不会在初始化阶段就触发看门狗超时。建议各模块的启动采用"先初始化基础设施（队列、缓存），再启动工作线程"的顺序，工作线程启动后先发送一次心跳，让看门狗知道线程已就绪。

**Day 5：性能优化 + 验收准备**

根据联调中发现的性能瓶颈进行优化。重点优化方向：帧调度延迟（目标：16 路摄像头全部在 11 秒内完成一轮推理）、消息队列积压（目标：正常运行时队列深度始终为 0）、内存峰值（目标：16 路摄像头全功能运行总内存占用 < 500MB）。整理所有测试报告和文档，准备验收材料。

技术说明：嵌入式设备的内存优化是永恒的话题。RK3568 平台最大 8GB RAM，但实际可用约 6~7GB（部分被内核和 GPU 占用）。主要内存消耗者：AI 模型（每个约 20~50MB）、帧缓冲（16 路 × 600KB ≈ 10MB）、异常图片缓冲（上限 1GB 在文件系统而非内存）、MQTT/HTTP 缓冲（约 10MB）。如果发现内存泄漏，优先检查帧数据的所有权转移是否正确、JPEG 编码后的 buffer 是否释放、RKNN context 是否在模型切换时正确销毁。

3. 全系统集成联调通过：所有业务流程和异常场景均验证通过。
