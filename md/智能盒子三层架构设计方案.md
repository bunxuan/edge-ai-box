## 智能盒子三层架构设计方案

### 一、架构总览

智能盒子软件系统采用经典的三层架构设计，自上而下依次为表示层（Presentation Layer）、业务层（Business Layer）和数据访问层（Data Access Layer）。三层之间通过定义清晰的 C 语言接口（结构体 + 函数指针表）进行交互，层间数据传递统一使用线程安全的消息队列，严格禁止跨层直接调用函数。软件架构与底层硬件平台完全解耦，三款芯片（RK3568 / RK3576 / RK3588）共享同一套业务逻辑代码，硬件差异通过硬件抽象层（HAL）封装在数据访问层内部，升级硬件平台时只需替换 HAL 实现和重新量化 AI 模型，无需修改上层任何代码。

### 二、各层职责概述

**表示层**是系统与外部世界沟通的窗口，承担两大职能：一是对外协议封装，包括 MQTT 客户端（连接物联网云平台）、MQTT 服务端（接收 ESP32/PLC 上报的传感器数据）、HTTP 服务端（局域网本地 RESTful API）和 HTTP 客户端（与云平台进行文件传输和数据上报）；二是多摄像头视频采集的统一管理，通过摄像头连接管理器（CameraConnectionManager）按 JSON 配置批量初始化各路摄像头的连接，支持 ONVIF 快照拉取单帧 JPEG 和 RTSP 硬件解码两种接入方式，所有采集到的帧统一封装为标准帧对象（含摄像头 ID、时间戳、原始图像数据），通过线程安全的帧分发队列送入业务层。表示层由两个线程驱动：UI 线程负责触摸屏渲染与交互，协议 I/O 线程基于 epoll 多路复用统一调度所有网络协议的异步收发。

**业务层**是系统的核心处理引擎，采用异步事件驱动机制。它从表示层接收帧数据和外部消息，完成 AI 推理、定时抓图、远程模型更新、运行日志管理、云端任务调度等核心业务。业务层通过消息处理线程、AI 推理线程和看门狗监控线程三个独立线程协同工作。在 RK3588 平台上，AI 推理线程可扩展为 2~3 个以实现 NPU 并行推理。

**数据访问层**是所有传感器和执行器设备的统一管理入口。它维护 JSON 格式的设备配置表，通过设备轮询线程基于时间轮的非阻塞调度方式读取 GPIO、RS485 Modbus、I2C、SPI 等各种接口上的设备状态，同时接收业务层下发的控制命令并执行。所有设备最新状态缓存在内存中供上层直接查询。底层硬件差异通过 HAL 封装，上层完全无感知。

### 三、层间交互设计（核心重点）

三层之间的交互遵循三条基本原则：第一，层间通信只通过预定义的 C 语言接口（结构体 + 函数指针表）进行，任何一层对另一层的调用都必须通过接口层完成，禁止跨层直接函数调用；第二，层间数据传递统一使用线程安全的消息队列，生产者写入、消费者取出，通过互斥锁和条件变量保证并发安全；第三，数据流向严格单向为主——帧数据自下而上（表示层 → 业务层），控制命令自上而下（业务层 → 数据访问层），查询结果自下而上（数据访问层 → 业务层），状态上报自下而上（业务层 → 表示层 → 云端）。

#### 3.1 表示层 → 业务层：消息上行

表示层向业务层传递数据有两条通道。

**接收消息队列**是主通道。协议 I/O 线程在 epoll 循环中收到外部消息后，将消息封装为统一的消息结构体写入接收消息队列。消息结构体定义如下：

```c
typedef struct {
    MsgType     type;        // 消息类型枚举
    int         camera_id;   // 关联摄像头ID（-1表示不关联）
    int         device_id;   // 关联设备ID（-1表示不关联）
    uint64_t    timestamp;   // clock_gettime(CLOCK_MONOTONIC) 单调时钟
    void       *payload;     // 消息载荷（按type解释为不同结构）
    size_t      payload_len; // 载荷长度
} LayerMessage;
```

消息类型涵盖以下几类：传感器数据上报消息（MQTT 服务端收到 ESP32/PLC 数据后转发）、云端管理指令消息（MQTT 客户端收到云平台下发的模型更新通知、抓图频率调整、日志级别切换、即时抓拍请求、摄像头增删配置等）、本地控制请求消息（HTTP 服务端收到的局域网用户操作请求）、以及设备状态变更通知。业务层的消息处理线程从该队列中取出消息，按 type 字段路由到对应的处理逻辑。

**帧分发队列**是第二条通道，专门用于视频帧数据的高效传输。表示层的摄像头连接管理器将每路摄像头采集到的帧封装为标准帧对象：

```c
typedef struct {
    int         camera_id;       // 摄像头ID
    uint64_t    capture_time;    // 采集时间戳（单调时钟）
    int         width, height;   // 图像尺寸
    int         format;          // 像素格式（NV12/NV21/RGB等）
    uint8_t    *data;            // 原始图像数据指针
    size_t      data_len;        // 数据长度
    FrameOwner  owner;           // 所有权标记
} VideoFrame;
```

帧数据通过所有权转移方式在层间传递——表示层将帧写入帧分发队列后即放弃该帧的写权限，业务层取出后成为唯一持有者，避免了额外的内存拷贝。帧分发队列采用有界环形缓冲设计，当队列满时丢弃最旧的帧（因为视频监控场景下最新帧永远比旧帧更有价值）。

#### 3.2 业务层 → 表示层：结果下行

业务层处理完成后需要将结果回传给表示层，由表示层负责对外发布。这条下行通道同样通过消息队列实现。

**发送消息队列**承载所有从业务层发往表示层的消息。消息处理线程将处理结果写入该队列，协议 I/O 线程从队列中取出后按目标协议分发到对应的网络端口。下行消息主要包括以下几类：

AI 检测结果上报——AI 推理线程完成一帧推理后，将检测结果（摄像头 ID、目标类别、置信度、边界框坐标）写入结果缓冲，同时生成上报消息放入发送消息队列，由 MQTT 客户端推送至物联网云平台。当检测到异常事件（烟火、人员摔倒等）时，异常图片（JPEG 编码后的原始帧）写入异常图片缓冲队列，由 HTTP 客户端异步上传至平台存档，严重告警优先于一般告警。

设备状态响应——当消息处理线程处理来自云平台或本地 HTTP 的状态查询请求时，从数据访问层获取设备最新缓存状态后，将查询结果封装为响应消息写入发送消息队列，由对应的协议端口（MQTT 或 HTTP）返回给请求方。

控制命令执行结果——业务层向数据访问层下发控制命令后，通过超时机制等待执行确认，获得结果后将执行成功或失败的状态封装为响应消息写入发送消息队列。

日志上报消息——日志系统定时将本地日志打包压缩后，通过发送消息队列通知 HTTP 客户端执行批量上传。

模型更新状态消息——模型下载进度、校验结果、加载成功或回退失败等信息，通过发送消息队列由 MQTT 客户端上报至云平台。

#### 3.3 业务层 → 数据访问层：命令下发

业务层对数据访问层的交互以控制命令下行为主，辅以状态查询。

**命令队列**是业务层向数据访问层下发控制指令的通道。当消息处理线程解析出设备控制命令（如开门禁、启动风扇、打开水泵等）后，将命令封装为设备控制结构体写入线程安全的命令队列：

```c
typedef struct {
    int         device_id;       // 目标设备ID
    CmdType     cmd_type;        // 控制命令类型
    void       *params;          // 命令参数
    uint64_t    timeout_ms;      // 超时时间（毫秒）
    CmdResult  *result;          // 执行结果回写指针
    sem_t      *done_sem;        // 信号量，用于同步等待结果
} DeviceCommand;
```

数据访问层的设备轮询线程在两次设备读取的间隙检查命令队列，取出命令后执行写操作。同一通信总线上的读写通过互斥锁保证不冲突，写命令优先执行以减少控制延迟。执行完成后轮询线程将结果写入 result 指针并通过 done_sem 信号量通知业务层。业务层采用超时等待机制，避免命令执行失败时阻塞后续消息处理。

**设备状态缓存**是数据访问层向业务层提供状态查询的机制。数据访问层的轮询线程按配置频率持续读取各传感器（门禁、水侵、温湿度等）的最新状态，并实时更新内存中的设备状态缓存表。业务层的状态查询无需等待下一次轮询周期，直接从缓存中读取即可，查询接口通过只读锁保护并发访问。对于关键设备（如门禁），在硬件支持中断通知时优先使用事件驱动模式，状态变化时数据访问层主动通过消息通知业务层，而非被动等待轮询。

#### 3.4 数据访问层 → 业务层：状态上报

数据访问层除了被动响应业务层的查询外，还会主动向业务层上报状态变更。

当设备轮询线程检测到以下情况时，会将事件消息写入表示层→业务层的接收消息队列（或直接写入业务层的内部事件队列）：设备离线告警（某设备连续通信超时超过阈值）、设备状态突变（如门禁从关闭变为打开、水侵传感器触发等关键事件）、以及控制命令执行异常（如写入超时、通信错误等）。这些上报消息的格式与表示层写入的消息统一使用 LayerMessage 结构体，业务层的消息处理线程以相同的方式处理，不区分消息来源。

#### 3.5 层间接口定义规范

三层之间的 C 语言接口统一采用"结构体 + 函数指针表"的模式定义，类似于面向对象语言中的接口/抽象类。以数据访问层对业务层暴露的接口为例：

```c
/* 数据访问层对外接口定义 */
typedef struct IDataAccess {
    /* 查询设备最新状态（从缓存读取，不触发轮询） */
    int  (*query_device_status)(int device_id, DeviceStatus *out);

    /* 下发控制命令（异步，通过信号量等待结果） */
    int  (*send_command)(DeviceCommand *cmd);

    /* 注册设备状态变更回调 */
    int  (*register_event_callback)(int device_id, EventCallback cb);

    /* 获取设备列表 */
    int  (*get_device_list)(DeviceDescriptor *list, int max_count);

    /* 热加载设备配置（运行时增删设备） */
    int  (*reload_config)(const char *config_path);
} IDataAccess;

/* 数据访问层初始化时返回接口实例 */
IDataAccess* data_access_create(const char *config_path);
```

表示层和业务层各自也有类似的接口定义。这种设计带来两个好处：一是层间依赖完全通过接口解耦，任何一层的内部实现可以自由重构，只要接口签名不变就不影响其他层；二是便于单元测试，测试时可以用 mock 实现替换真实接口。

### 四、数据流转全景

以一个典型的"烟火检测 → 云端告警"场景为例，完整描述数据在三层之间的流转过程。

首先，表示层的摄像头连接管理器通过 ONVIF 快照接口从某路摄像头拉取一帧 JPEG 图像，封装为 VideoFrame 标准帧对象，写入帧分发队列。业务层的帧调度器（FrameScheduler）从帧分发队列中取出该帧，根据该摄像头的优先级配置决定是否立即处理。若立即处理，帧数据送入预处理队列，AI 推理线程利用 RGA 硬件加速完成缩放和色彩空间转换后，调用 RKNN 框架在 NPU 上执行烟火检测模型推理。推理结果判定存在烟火，置信度 0.92。

AI 推理线程将检测结果写入结果缓冲（按摄像头 ID 索引），同时将原始帧 JPEG 编码后写入异常图片缓冲队列（烟火属于严重告警，优先级最高）。接着，推理线程生成一条 AI 检测结果消息写入发送消息队列。

表示层的协议 I/O 线程从发送消息队列中取出该消息，通过 MQTT 客户端将烟火告警推送至物联网云平台，同时通过 HTTP 客户端将异常图片异步上传至平台存档。整个过程中，数据访问层不参与此流程（因为烟火检测是纯视频 AI 分析，不涉及传感器设备）。

再以"远程开门禁"场景为例。云平台通过 MQTT 下发开门指令，表示层的 MQTT 客户端收到后写入接收消息队列。业务层的消息处理线程取出消息，解析为设备控制命令，校验权限后写入数据访问层的命令队列。数据访问层的轮询线程在间隙取出命令，通过 GPIO 接口驱动门禁继电器动作，执行完成后通过信号量通知业务层。业务层将执行结果写入发送消息队列，由 MQTT 客户端向云平台返回"开门成功"确认。

### 五、线程模型与层间协作

系统共 6 个线程（RK3588 平台可扩展至 7~8 个），按层分配如下：

表示层拥有 2 个线程。UI 线程专职触摸屏的界面渲染和触摸事件处理，它通过数据访问层提供的状态查询接口定期获取设备状态刷新界面显示，同时从业务层的发送消息队列中取出需要本地展示的消息（如告警提示）。协议 I/O 线程基于 epoll 多路复用机制，在单线程内统一调度 MQTT 客户端、MQTT 服务端、HTTP 服务端、HTTP 客户端以及所有摄像头的 ONVIF 快照/RTSP 连接的非阻塞收发，收到外部消息后写入业务层的接收消息队列或帧分发队列，同时从发送消息队列中取出待发数据写入对应协议端口。

业务层拥有 3 个线程（RK3588 可扩展至 4~5 个）。消息处理线程是业务层的入口，从接收消息队列中取出消息并路由到各功能模块。AI 推理线程专注多路视频帧的目标检测推理和异常图片生成。看门狗监控线程独立于其他业务线程，每秒检查各关键线程的心跳标记，任一线程超时未更新则尝试重启对应模块，严重时触发硬件看门狗重启整个系统。看门狗不集中在业务层内，而是分布在各层，避免业务层自身卡死时看门狗同时失效。

数据访问层拥有 1 个线程。设备轮询线程基于时间轮的非阻塞调度方式按配置频率读取各传感器状态，同时在两次读取间隙检查命令队列执行控制命令。

线程间的协作完全通过消息队列和互斥锁完成，不存在跨线程的直接函数调用。帧分发队列、接收消息队列、发送消息队列、命令队列这四条队列构成了线程间通信的主干道。

### 六、硬件抽象与平台解耦

三层架构的一个核心设计目标是软件与硬件平台解耦。这一目标通过硬件抽象层（HAL）实现，HAL 位于数据访问层内部，对上提供统一的设备操作接口，对下封装具体芯片的驱动差异。

以视频解码为例，RK3568 的硬件解码器支持 H.265/H.264 4K@60fps，RK3576 支持 4K@120fps，RK3588 支持 8K@30fps 或 4K@120fps，三者的解码器驱动接口各不相同。HAL 将解码操作抽象为"输入压缩码流 → 输出解码帧"的统一接口，表示层的摄像头连接管理器调用 HAL 接口时不需要知道底层是哪款芯片的解码器。

以 NPU 推理为例，三款芯片的 NPU 架构和 RKNN 运行时库版本不同，HAL 将推理操作抽象为"加载模型 → 输入帧 → 输出检测结果"的统一接口，业务层的 AI 推理线程调用 HAL 接口时不需要关心 NPU 的具体型号和算力差异。

以 RGA 图形加速为例，HAL 将缩放、色彩空间转换、ROI 裁剪等操作抽象为统一接口，业务层的预处理模块调用时不需要知道 RGA 的具体寄存器配置。

当系统从 RK3568 升级到 RK3576 或 RK3588 时，只需替换 HAL 的实现文件、重新量化 AI 模型（RK3568 用 INT8 轻量模型，RK3576/RK3588 可用 INT8 或 FP16 较大模型）、调整配置参数（如最大摄像头数量、帧槽位预分配数），表示层和业务层的代码完全不需要修改。

### 七、配置驱动与热加载

三层架构的所有可变参数均通过 JSON 配置文件管理，支持运行时热加载，无需重启系统。

表示层的协议端口参数（MQTT 地址/端口/认证信息、HTTP 端口/Token 等）统一存储在协议配置文件中，由协议配置管理类在启动时读取，通过工厂模式动态创建各协议实例。摄像头接入配置（摄像头 ID、RTSP/ONVIF 地址、分辨率、抽帧间隔、检测业务类型等）存储在独立的摄像头配置文件中，连接管理器启动时批量初始化，运行时支持通过 MQTT 指令或 HTTP 接口动态增删摄像头。

业务层的调度策略参数（优先级配置、超时阈值、日志级别、上传频率等）存储在业务配置文件中，支持云端远程下发修改并热加载。

数据访问层的设备配置表（设备名称、通信接口类型、地址、轮询频率、超时时间、数据类型和换算规则）以 JSON 格式存储，轮询线程支持配置热加载，新增设备自动纳入轮询调度，移除设备自动释放资源。

这种配置驱动的设计使得三层架构在部署到不同项目场景时，只需修改配置文件即可适配，无需重新编译代码，极大提升了系统的灵活性和可维护性。
