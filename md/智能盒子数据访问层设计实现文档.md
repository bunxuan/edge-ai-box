## 智能盒子数据访问层设计实现文档

---

### 一、数据访问层整体结构

数据访问层是智能盒子与物理世界交互的根基，承担三大职能：传感器设备状态的周期性采集与缓存、执行器设备的控制命令接收与执行、以及底层硬件差异的统一抽象封装。整个数据访问层由一个设备轮询线程驱动，内部共 12 个类协同工作。

数据访问层只有一个线程——DevicePollingThread，但它承载了三项并行职责：周期性传感器轮询、控制命令执行、中断事件处理。三项职责在同一个主循环中通过"轮询间隙检查命令队列"和"epoll 监听中断 fd"的方式统一调度，不需要额外的线程。这种单线程设计在嵌入式环境下有显著优势：调试简单、资源占用低、不存在设备驱动层面的线程安全问题（同一总线上的读写通过互斥锁串行化即可）。

数据访问层与外层的交互通过三条层间通道完成。CommandQueue 是业务层向数据访问层下发控制命令的入口，DevicePollingThread 在轮询间隙从中取出命令执行；DeviceStatusCache 是数据访问层向业务层和表示层提供设备状态查询的共享缓存，轮询线程持续更新，上层直接读取；UpstreamMessageQueue 是数据访问层向业务层上报设备告警（离线、状态突变、命令执行异常）的消息通道。

---

### 二、DevicePollingThread 设备轮询线程

DevicePollingThread 是数据访问层的心脏，也是整个系统与物理设备交互的唯一线程。它基于时间轮的非阻塞调度模型，在单线程内统一完成传感器状态采集、控制命令执行和中断事件处理三项任务。

#### 2.1 类定义

```cpp
class DevicePollingThread {
public:
    DevicePollingThread(
        // ── 层间通道 ──
        CommandQueue           *cmd_queue,            // 命令入口（← 业务层）
        DeviceStatusCache      *device_cache,         // 状态缓存（→ 业务层/表示层）
        UpstreamMessageQueue   *upstream_queue,       // 告警出口（→ 业务层）
        // ── 内部模块 ──
        DeviceConfigManager    *config_manager,       // 设备配置管理
        InterruptEventHandler  *interrupt_handler     // 中断事件处理
    );

    void start();     // 启动轮询线程
    void stop();      // 停止（优雅退出）

private:
    void polling_loop();                        // 主循环
    void execute_polling_round();               // 执行一轮设备轮询
    bool execute_command_if_available();        // 间隙检查并执行命令
    void process_interrupt_events();            // 处理中断事件

    // ── 时间轮调度 ──
    struct PollingEntry {
        int          device_id;
        DeviceDriver *driver;           // 对应的设备驱动
        uint32_t     interval_ms;       // 轮询间隔（毫秒）
        uint64_t     next_poll_time;    // 下次应轮询时间（单调时钟）
        int          timeout_count;     // 连续超时计数
        bool         enabled;           // 是否启用
    };

    void rebuild_time_wheel();                      // 从配置重建时间轮
    int  select_next_device(uint64_t now);          // 选取下一个就绪设备
    void handle_poll_timeout(int device_id);        // 处理设备超时
    void handle_poll_success(int device_id,
                             const DeviceStatus &status);  // 处理轮询成功

    // ── 总线互斥 ──
    struct BusMutex {
        pthread_mutex_t lock;
        CommInterface   bus_type;       // RS485_1 / RS485_2 / I2C_1 / ...
        int             active_device;  // 当前占用总线的设备ID（-1=空闲）
    };
    BusMutex* get_bus_mutex(CommInterface iface);
    bool try_lock_bus(CommInterface iface, int device_id);
    void unlock_bus(CommInterface iface);

    // ── 时间轮 ──
    std::vector<PollingEntry>  time_wheel_;          // 时间轮条目
    pthread_mutex_t            wheel_mutex_;         // 保护时间轮的互斥锁
    int                        wheel_cursor_;        // 当前扫描游标

    // ── 总线互斥表 ──
    std::unordered_map<int, BusMutex>  bus_mutex_table_;  // 按总线类型索引

    // ── 层间通道指针 ──
    CommandQueue           *cmd_queue_;
    DeviceStatusCache      *device_cache_;
    UpstreamMessageQueue   *upstream_queue_;

    // ── 内部模块指针 ──
    DeviceConfigManager    *config_manager_;
    InterruptEventHandler  *interrupt_handler_;

    // ── epoll（用于中断fd监听）──
    int                    epoll_fd_;
    struct epoll_event     events_[16];

    // ── 心跳 ──
    std::atomic<uint64_t>  heartbeat_;

    // ── 统计 ──
    uint64_t  poll_success_count_;      // 轮询成功总次数
    uint64_t  poll_timeout_count_;      // 轮询超时总次数
    uint64_t  cmd_executed_count_;      // 已执行命令总数
    uint64_t  cmd_failed_count_;        // 执行失败命令总数
};
```

#### 2.2 主循环设计

polling_loop 是 DevicePollingThread 的核心执行逻辑，采用"时间轮扫描 → 设备轮询 → 间隙命令执行 → 中断处理"的循环模式。每次迭代的完整流程如下：

```
polling_loop() 单次迭代：
│
├─① 获取当前时间 now = get_monotonic_ms()
│
├─② 时间轮扫描：遍历 time_wheel_ 找到所有 next_poll_time <= now 的设备
│   for each ready_entry:
│     if entry.enabled == false → 跳过
│     尝试获取该设备所属总线的互斥锁
│     if 总线被其他设备占用 → 跳过（稍后重试）
│     调用 entry.driver->read() 发起非阻塞读取
│     更新 entry.next_poll_time = now + entry.interval_ms
│
├─③ 收集已完成的读取结果（非阻塞轮询的回调/完成检测）
│   for each completed_read:
│     if 读取成功:
│       解析设备状态 → handle_poll_success()
│       更新 DeviceStatusCache
│       重置 timeout_count = 0
│     if 读取超时/失败:
│       handle_poll_timeout()
│       timeout_count++
│       if timeout_count >= OFFLINE_THRESHOLD:
│         DeviceStatusCache::mark_offline()
│         发送 MSG_DEVICE_EVENT 到 UpstreamMessageQueue
│     释放总线互斥锁
│
├─④ execute_command_if_available()
│   检查 CommandQueue 是否有待执行命令
│   if 有命令:
│     检查命令目标设备的总线是否空闲
│     if 总线空闲:
│       锁定总线 → 执行命令 → 回写结果 → sem_signal → 释放总线
│     if 总线被占用:
│       跳过，下次循环再检查（不阻塞轮询）
│
├─⑤ process_interrupt_events()
│   epoll_wait(epoll_fd_, events_, 16, 0)  非阻塞检查
│   for each ready_event:
│     interrupt_handler_->handle(event.fd)
│
└─⑥ 更新心跳标记
    heartbeat_.store(get_monotonic_ms())
```

这个循环的关键设计点有四个。第一，设备轮询采用非阻塞方式——read() 调用发起读取后立即返回，不等待硬件响应。实际的读取完成检测通过检查驱动的 is_ready() 方法或在下一次循环迭代中确认。这保证了单个设备的通信超时不会阻塞整个轮询线程。第二，命令执行放在轮询间隙（步骤④），即在处理完就绪的轮询设备之后、检查命令队列。如果命令目标设备的总线正被轮询占用，命令会等待下一轮循环，但不会阻塞轮询本身。第三，中断事件处理使用独立的 epoll fd，通过非阻塞 epoll_wait（timeout=0）检查，有中断事件就处理，没有就跳过，零开销。第四，时间轮的扫描是游标式的——wheel_cursor_ 记录上次扫描位置，每次从游标位置开始扫描，避免每次都从头遍历。

#### 2.3 时间轮调度算法

时间轮是设备轮询调度的核心数据结构。每个 PollingEntry 代表一个需要周期性读取的设备，包含设备ID、驱动指针、轮询间隔和下次轮询时间。调度器的任务是高效找到所有"到期"的设备（next_poll_time <= 当前时间）。

```cpp
void DevicePollingThread::execute_polling_round() {
    uint64_t now = get_monotonic_ms();
    int checked = 0;
    int wheel_size = time_wheel_.size();

    pthread_mutex_lock(&wheel_mutex_);

    // 从游标位置开始扫描，最多扫描一圈
    for (int i = 0; i < wheel_size && checked < wheel_size; i++) {
        int idx = (wheel_cursor_ + i) % wheel_size;
        PollingEntry &entry = time_wheel_[idx];
        checked++;

        if (!entry.enabled) continue;

        // 检查是否到期
        if (entry.next_poll_time > now) continue;

        // 检查总线是否空闲
        CommInterface bus = entry.driver->get_bus_interface();
        if (!try_lock_bus(bus, entry.device_id)) {
            // 总线被占用，跳过，下次循环再试
            continue;
        }

        // 发起非阻塞读取
        DeviceStatus status;
        int ret = entry.driver->read_nonblock(entry.device_id, &status);

        if (ret == DRIVER_OK) {
            // 读取成功（立即返回结果的场景：GPIO/I2C等快速总线）
            handle_poll_success(entry.device_id, status);
            entry.timeout_count = 0;
            entry.next_poll_time = now + entry.interval_ms;
            unlock_bus(bus);

        } else if (ret == DRIVER_PENDING) {
            // 读取已发起但尚未完成（RS485 Modbus等慢速总线）
            // 不释放总线锁，在步骤③中检查完成状态后释放
            entry.next_poll_time = now + entry.interval_ms;
            // 总线锁在完成处理时释放

        } else {
            // 读取失败
            handle_poll_timeout(entry.device_id);
            entry.timeout_count++;
            unlock_bus(bus);

            if (entry.timeout_count >= OFFLINE_THRESHOLD) {
                device_cache_->mark_offline(entry.device_id);

                // 通过上行消息队列上报告警
                LayerMessage alert;
                alert.type = MSG_DEVICE_EVENT;
                alert.device_id = entry.device_id;
                alert.timestamp = get_monotonic_us();
                DeviceEventPayload payload = {
                    .event_type = DEVICE_OFFLINE,
                    .device_id = entry.device_id,
                    .consecutive_timeouts = entry.timeout_count
                };
                alert.payload = malloc(sizeof(DeviceEventPayload));
                memcpy(alert.payload, &payload, sizeof(DeviceEventPayload));
                alert.payload_len = sizeof(DeviceEventPayload);
                upstream_queue_->push(alert);

                LOG_WARN("Device %d offline after %d consecutive timeouts",
                         entry.device_id, entry.timeout_count);
            }
        }
    }

    // 更新游标
    wheel_cursor_ = (wheel_cursor_ + checked) % wheel_size;

    pthread_mutex_unlock(&wheel_mutex_);
}
```

时间轮调度的核心思想是"每个设备独立计时、到期才读"。与传统的"遍历所有设备逐个读取"不同，时间轮只处理到期的设备，未到期的设备零开销。假设系统有 50 个传感器，其中大部分轮询间隔为 5 秒，少数为 1 秒，那么在任意一个循环迭代中，通常只有 2~3 个设备到期需要处理，其余 47~48 个设备只需一次时间比较即可跳过。

轮询间隔的设定通过 JSON 配置文件指定，不同设备可以有不同的轮询频率。例如门禁设备可能配置为 500ms（高频监测），温湿度传感器配置为 5000ms（低频采样），水侵传感器配置为 1000ms。配置修改后通过热加载机制重建时间轮，无需重启系统。

#### 2.4 命令执行引擎

命令执行是 DevicePollingThread 的第二项职责。在每轮设备轮询的间隙（步骤④），线程检查 CommandQueue 是否有待执行的命令。命令执行采用"写优先"策略——如果命令目标设备的总线当前空闲，立即执行写操作，即使这意味着推迟下一次轮询。

```cpp
bool DevicePollingThread::execute_command_if_available() {
    DeviceCommand *cmd = cmd_queue_->try_pop();
    if (cmd == nullptr) return false;

    // 查找目标设备的驱动
    PollingEntry *entry = find_entry(cmd->device_id);
    if (entry == nullptr) {
        // 设备不存在，立即返回失败
        CmdResult fail_result = {.success = false, .error = "DEVICE_NOT_FOUND"};
        cmd_queue_->complete(cmd, fail_result);
        cmd_failed_count_++;
        return true;
    }

    DeviceDriver *driver = entry->driver;
    CommInterface bus = driver->get_bus_interface();

    // 检查总线是否空闲（轮询可能正在占用）
    if (!try_lock_bus(bus, cmd->device_id)) {
        // 总线被轮询占用，将命令放回队列头部，下次循环再试
        cmd_queue_->push_front(cmd);
        return false;
    }

    // 执行控制命令
    CmdResult result = {};
    int ret = driver->write_command(cmd->device_id, cmd->cmd_type,
                                    cmd->params, &result);

    unlock_bus(bus);

    if (ret == DRIVER_OK && result.success) {
        cmd_executed_count_++;
        LOG_INFO("DevicePolling", "Command %d executed on device %d: OK",
                 cmd->cmd_type, cmd->device_id);
    } else {
        cmd_failed_count_++;
        LOG_WARN("DevicePolling", "Command %d failed on device %d: %s",
                 cmd->cmd_type, cmd->device_id,
                 result.success ? "DRIVER_ERROR" : result.error);
    }

    // 回写结果并唤醒业务层
    cmd_queue_->complete(cmd, result);

    return true;
}
```

命令执行的关键设计点在于总线互斥。当一条 RS485 总线上挂了多个 Modbus 设备时，同一时刻只能有一个设备进行通信。try_lock_bus 检查总线是否被当前轮询操作占用：如果占用，命令不会阻塞等待，而是放回队列头部（push_front），让轮询操作先完成，下一轮循环时命令优先被取出执行。这种设计保证了轮询的连续性不被命令执行打断，同时命令也能在很短时间内得到执行。

对于 GPIO 设备，总线互斥的粒度是单个 GPIO 引脚，不同引脚之间不存在冲突，因此 GPIO 总线上的读写可以并行。对于 I2C 设备，总线互斥的粒度是 I2C 总线编号（同一 I2C 控制器下的所有设备互斥）。对于 SPI 设备，总线互斥的粒度是 SPI 片选信号（CS），不同 CS 的设备可以并行。

#### 2.5 设备超时与离线检测

设备离线检测通过连续超时计数实现。每个 PollingEntry 维护一个 timeout_count 字段，每次轮询失败（通信超时或驱动返回错误）时递增，成功时归零。当 timeout_count 达到阈值（OFFLINE_THRESHOLD，默认 3 次）时，设备被标记为离线。

```cpp
void DevicePollingThread::handle_poll_timeout(int device_id) {
    poll_timeout_count_++;

    // 更新缓存中的超时计数（但不标记离线，由调用方判断阈值）
    DeviceStatus status;
    if (device_cache_->get(device_id, &status)) {
        status.last_update = get_monotonic_us();
        // timeout_count 在 PollingEntry 中维护，不直接写入 DeviceStatus
        device_cache_->update(device_id, status);
    }
}

void DevicePollingThread::handle_poll_success(int device_id,
                                               const DeviceStatus &status) {
    poll_success_count_++;

    // 更新设备状态缓存
    DeviceStatus cached_status = status;
    cached_status.last_update = get_monotonic_us();
    cached_status.online = true;
    device_cache_->update(device_id, cached_status);

    // 检查是否从离线恢复
    PollingEntry *entry = find_entry(device_id);
    if (entry && entry->timeout_count > 0) {
        LOG_INFO("DevicePolling", "Device %d recovered (was offline for %d polls)",
                 device_id, entry->timeout_count);

        // 上报恢复事件
        LayerMessage event;
        event.type = MSG_DEVICE_EVENT;
        event.device_id = device_id;
        event.timestamp = get_monotonic_us();
        DeviceEventPayload payload = {
            .event_type = DEVICE_RECOVERED,
            .device_id = device_id,
            .consecutive_timeouts = 0
        };
        event.payload = malloc(sizeof(DeviceEventPayload));
        memcpy(event.payload, &payload, sizeof(DeviceEventPayload));
        event.payload_len = sizeof(DeviceEventPayload);
        upstream_queue_->push(event);
    }
}
```

离线检测的设计遵循"宁可误报、不可漏报"的原则——阈值设为 3 次连续超时，对于 5 秒轮询间隔的设备意味着 15 秒无响应即判定离线。这个阈值在设备配置表中可以按设备单独调整，对于通信环境较差的 RS485 设备可以适当放宽到 5 次。

设备从离线状态恢复时（连续超时后首次成功读取），系统同样通过 UpstreamMessageQueue 上报恢复事件，业务层可以据此触发"设备恢复"通知。

### 三、DeviceConfigManager 设备配置管理器

DeviceConfigManager 负责设备配置的加载、解析和热加载。它读取 JSON 格式的设备配置文件，通过工厂模式创建对应的 DeviceDriver 实例，并在运行时支持配置变更的无缝生效。

#### 3.1 类定义

#### 3.3 热加载机制

热加载是 DeviceConfigManager 的关键特性。当配置文件发生变化时（通过 inotify 监控文件修改或收到业务层的 reload 命令），DeviceConfigManager 重新加载配置并与当前配置进行差异比较，生成 ConfigDiff 结构体，然后通过回调通知 DevicePollingThread 执行增删操作。

```cpp
bool DeviceConfigManager::reload_config() {
    // ① 解析新配置到临时变量（不修改当前 entries_）
    std::vector<DeviceEntry> new_entries;
    if (!load_and_parse(config_path_, &new_entries)) {
        LOG_ERROR("DeviceConfig", "Failed to parse config file: %s",
                  config_path_.c_str());
        return false;
    }

    if (!validate_config(new_entries)) {
        LOG_ERROR("DeviceConfig", "Config validation failed");
        return false;
    }

    // ② 计算差异
    pthread_rwlock_rdlock(&entries_lock_);
    ConfigDiff diff = compute_diff(entries_, new_entries);
    pthread_rwlock_unlock(&entries_lock_);

    // ③ 应用变更（写锁）
    pthread_rwlock_wrlock(&entries_lock_);
    entries_ = std::move(new_entries);
    pthread_rwlock_unlock(&entries_lock_);

    // ④ 通知轮询线程
    if (change_callback_) {
        change_callback_(change_context_, ConfigChange{
            .added_ids = diff.added_ids,
            .removed_ids = diff.removed_ids,
            .changed_ids = diff.changed_ids
        });
    }

    LOG_INFO("DeviceConfig", "Config reloaded: +%d -%d ~%d devices",
             diff.added_ids.size(), diff.removed_ids.size(),
             diff.changed_ids.size());

    return true;
}
```

热加载的关键设计点在于"先解析后切换"——新配置先完整解析到临时变量中，验证通过后才替换当前配置。如果新配置文件格式错误或缺少必要字段，热加载失败，当前配置不受影响。差异比较（compute_diff）按 device_id 匹配，识别新增、移除和配置变更三类操作，DevicePollingThread 收到通知后分别执行时间轮条目增删和驱动实例创建销毁。

### 四、DeviceDriver 设备驱动体系

DeviceDriver 是所有设备驱动的抽象基类，定义了设备读写的统一接口。不同通信接口（GPIO/RS485/I2C/SPI）的设备通过继承 DeviceDriver 实现各自的驱动逻辑。DevicePollingThread 通过 DeviceDriver 接口与设备交互，不需要了解底层通信协议细节。

#### 4.1 DeviceDriver 抽象基类

```cpp
class DeviceDriver {
public:
    virtual ~DeviceDriver() = default;

    // ── 生命周期 ──
    virtual bool init(const JsonObject &config) = 0;     // 初始化（读取配置、打开设备文件）
    virtual void close() = 0;                             // 关闭（释放硬件资源）

    // ── 非阻塞读取（轮询用）──
    virtual int  read_nonblock(int device_id, DeviceStatus *out) = 0;
    //   返回 DRIVER_OK:      读取成功，out 已填充
    //   返回 DRIVER_PENDING: 读取已发起，等待完成（慢速总线）
    //   返回 DRIVER_ERROR:   读取失败

    // ── 检查非阻塞读取是否完成（慢速总线用）──
    virtual bool is_ready(int device_id) { return true; }

    // ── 控制命令写入 ──
    virtual int  write_command(int device_id, CmdType cmd_type,
                               void *params, CmdResult *out) = 0;
    //   返回 DRIVER_OK:    写入成功
    //   返回 DRIVER_ERROR: 写入失败

    // ── 查询接口 ──
    virtual CommInterface get_bus_interface() const = 0;    // 所属总线类型
    virtual const char*   driver_name() const = 0;          // 驱动名称（日志用）
    virtual int           get_timeout_ms(int device_id) const = 0;

protected:
    // ── 数据换算（子类可重写）──
    virtual double convert_raw_value(int raw_value,
                                     const std::string &rule) {
        // 默认：线性换算 value * scale + offset
        // 子类可按需重写为更复杂的换算逻辑
        return static_cast<double>(raw_value);
    }
};
```

DeviceDriver 的设计遵循"一个驱动类对应一种通信总线"的原则，而非"一个驱动类对应一种设备"。这意味着 GPIODriver 既驱动门禁也驱动水侵传感器，只要它们都接在 GPIO 上。设备类型的差异（门禁是开关量、温湿度是模拟量）通过 DeviceDescriptor 的 data_type 和 convert_rule 字段描述，驱动只负责原始数据的读写，数据换算由驱动基类的 convert_raw_value 方法根据 convert_rule 完成。

#### 4.2 GPIODriver 实现

GPIODriver 封装 Linux sysfs GPIO 接口和 /dev/gpiochip 字符设备接口，支持输入（传感器读取）和输出（执行器控制）两种模式。

```cpp
class GPIODriver : public DeviceDriver {
public:
    bool init(const JsonObject &config) override;
    void close() override;

    int  read_nonblock(int device_id, DeviceStatus *out) override;
    int  write_command(int device_id, CmdType cmd_type,
                       void *params, CmdResult *out) override;

    CommInterface get_bus_interface() const override { return COMM_GPIO; }
    const char*   driver_name() const override { return "GPIO"; }
    int           get_timeout_ms(int device_id) const override { return 100; }

    // ── GPIO 专用方法 ──
    bool setup_interrupt(int device_id, const char *edge,
                         int *out_epoll_fd);     // 配置中断并返回 epoll fd
    int  read_interrupt_value(int device_id);    // 中断触发后读取当前值

private:
    struct GPIODevice {
        int         gpio_number;         // GPIO 编号（如 45 对应 GPIO_45）
        int         fd;                  // /dev/gpiochipN 或 /sys/class/gpio/gpioN/value 的文件描述符
        bool        is_input;            // true=输入(传感器), false=输出(执行器)
        int         active_level;        // 有效电平：0=低有效, 1=高有效
        bool        interrupt_enabled;   // 是否启用中断
    };

    std::unordered_map<int, GPIODevice>  devices_;   // device_id → GPIO设备信息
    pthread_mutex_t                      gpio_mutex_;

    // ── sysfs 操作辅助 ──
    int  gpio_export(int gpio_number);
    int  gpio_set_direction(int gpio_number, const char *direction);
    int  gpio_set_edge(int gpio_number, const char *edge);
    int  gpio_read_value(int fd);
    int  gpio_write_value(int fd, int value);
};
```

GPIODriver 的 read_nonblock 实现非常直接——通过 pread 读取 sysfs value 文件获取当前电平状态，根据 active_level 换算为逻辑值（0/1），填充 DeviceStatus 返回。由于 GPIO 操作是内存映射的文件 I/O，读写都在微秒级完成，不存在 PENDING 状态。

write_command 用于控制 GPIO 输出设备（如门禁继电器、风扇开关）。收到开门命令时，将对应 GPIO 引脚置为有效电平，延时指定时间后自动恢复（如门禁继电器吸合 2 秒后释放）。延时由驱动内部的定时器管理，不阻塞轮询线程。

```cpp
int GPIODriver::read_nonblock(int device_id, DeviceStatus *out) {
    auto it = devices_.find(device_id);
    if (it == devices_.end()) return DRIVER_ERROR;

    GPIODevice &dev = it->second;
    int raw_value = gpio_read_value(dev.fd);
    if (raw_value < 0) return DRIVER_ERROR;

    // 按有效电平换算
    int logical_value = (raw_value == dev.active_level) ? 1 : 0;

    out->device_id = device_id;
    out->type = GPIO_SENSOR;
    out->iface = COMM_GPIO;
    out->online = true;
    out->switch_state = (logical_value != 0);
    out->value = logical_value;

    return DRIVER_OK;
}

int GPIODriver::write_command(int device_id, CmdType cmd_type,
                               void *params, CmdResult *out) {
    auto it = devices_.find(device_id);
    if (it == devices_.end()) {
        out->success = false;
        out->error = "DEVICE_NOT_FOUND";
        return DRIVER_ERROR;
    }

    GPIODevice &dev = it->second;
    pthread_mutex_lock(&gpio_mutex_);

    switch (cmd_type) {
        case CMD_OPEN_DOOR: {
            // 置为有效电平 → 延时恢复
            gpio_write_value(dev.fd, dev.active_level);
            // 启动延时恢复定时器（2秒后恢复为无效电平）
            schedule_restore_timer(device_id, 2000);
            out->success = true;
            break;
        }
        case CMD_SET_SWITCH: {
            int target_value = *(int*)params;
            gpio_write_value(dev.fd, target_value ? dev.active_level
                                                   : (1 - dev.active_level));
            out->success = true;
            break;
        }
        case CMD_START_FAN:
        case CMD_START_PUMP: {
            gpio_write_value(dev.fd, dev.active_level);
            out->success = true;
            break;
        }
        case CMD_STOP_FAN:
        case CMD_STOP_PUMP: {
            gpio_write_value(dev.fd, 1 - dev.active_level);
            out->success = true;
            break;
        }
        default:
            out->success = false;
            out->error = "UNSUPPORTED_CMD";
            pthread_mutex_unlock(&gpio_mutex_);
            return DRIVER_ERROR;
    }

    pthread_mutex_unlock(&gpio_mutex_);
    return DRIVER_OK;
}
```

GPIO 中断配置是 GPIODriver 的特殊功能。对于配置了 interrupt_enabled 的关键设备（如门禁、水侵），GPIODriver 在 init 阶段通过 sysfs 配置 GPIO 边沿触发中断，打开 value 文件的 O_RDWR 句柄，将 fd 注册到 DevicePollingThread 的 epoll 中。当 GPIO 电平变化触发中断时，epoll 通知 DevicePollingThread，InterruptEventHandler 读取当前电平值并上报告警消息。

#### 4.3 ModbusRTUDriver 实现

ModbusRTUDriver 封装 RS485 总线上的 Modbus RTU 协议通信，用于连接温湿度传感器、电表、PLC 等工业设备。RS485 是半双工总线，同一时刻只能有一个方向的数据传输，因此总线互斥在这一层尤为重要。

```cpp
class ModbusRTUDriver : public DeviceDriver {
public:
    bool init(const JsonObject &config) override;
    void close() override;

    int  read_nonblock(int device_id, DeviceStatus *out) override;
    bool is_ready(int device_id) override;
    int  write_command(int device_id, CmdType cmd_type,
                       void *params, CmdResult *out) override;

    CommInterface get_bus_interface() const override { return bus_id_; }
    const char*   driver_name() const override { return "ModbusRTU"; }
    int           get_timeout_ms(int device_id) const override;

private:
    struct ModbusDevice {
        int         slave_addr;          // Modbus 从站地址
        int         register_addr;       // 起始寄存器地址
        int         register_count;      // 寄存器数量
        int         function_code;       // 功能码（3=读保持寄存器, 6=写单寄存器, 16=写多寄存器）
        std::string convert_rule;        // 数据换算规则
        uint16_t    read_buffer[64];     // 读取缓冲区
        bool        read_pending;        // 是否有未完成的读取
        uint64_t    read_start_time;     // 读取发起时间（超时检测）
    };

    // ── RS485 串口操作 ──
    int  serial_fd_;                     // /dev/ttySx 文件描述符
    CommInterface bus_id_;               // RS485_1 / RS485_2 等

    // ── Modbus 协议操作 ──
    int  modbus_send_read_request(int slave_addr, int func_code,
                                   int reg_addr, int reg_count);
    int  modbus_send_write_request(int slave_addr, int func_code,
                                    int reg_addr, const uint16_t *values,
                                    int count);
    int  modbus_parse_response(uint8_t *buf, int len,
                                uint16_t *out_regs, int max_regs);
    bool modbus_check_crc(const uint8_t *buf, int len);

    // ── RS485 方向控制 ──
    void rs485_enable_transmitter();     // 切换为发送模式
    void rs485_enable_receiver();        // 切换为接收模式

    std::unordered_map<int, ModbusDevice>  devices_;
    pthread_mutex_t                        modbus_mutex_;
};
```

ModbusRTUDriver 的 read_nonblock 实现体现了"非阻塞"在慢速总线上的含义。RS485 Modbus 通信涉及串口发送请求帧、等待从站响应、接收响应帧三个步骤，整个过程可能需要 50~200ms。驱动的做法是：第一次调用 read_nonblock 时构造并发送 Modbus 读请求帧，将 read_pending 置为 true，返回 DRIVER_PENDING；后续调用 is_ready 检查是否收到完整响应帧或超时；响应到达后由 read_nonblock 的后续调用解析响应并返回 DRIVER_OK。

```cpp
int ModbusRTUDriver::read_nonblock(int device_id, DeviceStatus *out) {
    auto it = devices_.find(device_id);
    if (it == devices_.end()) return DRIVER_ERROR;

    ModbusDevice &dev = it->second;

    // 如果之前有未完成的读取，检查是否已完成
    if (dev.read_pending) {
        uint64_t now = get_monotonic_ms();
        if (now - dev.read_start_time > get_timeout_ms(device_id)) {
            // 超时
            dev.read_pending = false;
            rs485_enable_receiver();
            return DRIVER_ERROR;
        }

        // 尝试读取响应
        uint8_t resp_buf[256];
        int n = read(serial_fd_, resp_buf, sizeof(resp_buf));
        if (n <= 0) {
            return DRIVER_PENDING;   // 还没收到，继续等待
        }

        // 解析响应
        if (!modbus_check_crc(resp_buf, n)) {
            dev.read_pending = false;
            rs485_enable_receiver();
            return DRIVER_ERROR;
        }

        int parsed = modbus_parse_response(resp_buf, n,
                                            dev.read_buffer, 64);
        if (parsed < 0) {
            dev.read_pending = false;
            rs485_enable_receiver();
            return DRIVER_ERROR;
        }

        dev.read_pending = false;
        rs485_enable_receiver();

        // 数据换算
        double value = convert_raw_value(dev.read_buffer[0],
                                          dev.convert_rule);

        out->device_id = device_id;
        out->type = ANALOG_SENSOR;
        out->iface = bus_id_;
        out->online = true;
        out->value = value;

        return DRIVER_OK;
    }

    // 首次调用：发送读请求
    rs485_enable_transmitter();
    int ret = modbus_send_read_request(dev.slave_addr, dev.function_code,
                                        dev.register_addr,
                                        dev.register_count);
    if (ret < 0) {
        rs485_enable_receiver();
        return DRIVER_ERROR;
    }

    // 切换为接收模式，等待从站响应
    rs485_enable_receiver();
    dev.read_pending = true;
    dev.read_start_time = get_monotonic_ms();

    return DRIVER_PENDING;
}

bool ModbusRTUDriver::is_ready(int device_id) {
    auto it = devices_.find(device_id);
    if (it == devices_.end()) return false;

    ModbusDevice &dev = it->second;
    if (!dev.read_pending) return true;

    // 检查串口是否有数据可读（通过 select 非阻塞检查）
    fd_set rfds;
    FD_ZERO(&rfds);
    FD_SET(serial_fd_, &rfds);
    struct timeval tv = {0, 0};
    int ret = select(serial_fd_ + 1, &rfds, nullptr, nullptr, &tv);
    return (ret > 0);
}
```

RS485 方向控制是 Modbus 通信的关键细节。RS485 收发器通过 DE/RE 引脚控制发送/接收方向。在发送 Modbus 请求帧前，驱动通过 GPIO 将 DE 引脚置高（发送模式）；发送完成后将 DE 引脚拉低（接收模式），等待从站响应。这个切换过程在微秒级完成，但对通信正确性至关重要。

write_command 的实现与 read_nonblock 类似，区别在于发送的是 Modbus 写请求帧（功能码 6 或 16）。由于写操作不需要等待大量响应数据（从站只返回一个简短的确认帧），写操作的完成通常比读操作更快。

#### 4.4 I2CDriver 与 SPIDriver 实现

I2CDriver 和 SPIDriver 的实现结构与 GPIODriver 类似，区别在于底层通信接口的操作方式。

### 五、InterruptEventHandler 中断事件处理器

InterruptEventHandler 负责处理关键设备（如门禁、水侵传感器）的硬件中断事件。这些设备对实时性要求极高——门禁被强行打开、水侵传感器触发等事件必须在毫秒级被捕获并上报，不能等待下一次轮询周期。

#### 5.1 类定义

```cpp
class InterruptEventHandler {
public:
    InterruptEventHandler(
        UpstreamMessageQueue *upstream_queue,
        DeviceStatusCache    *device_cache
    );
    ~InterruptEventHandler();

    // ── 中断注册/注销 ──
    bool register_interrupt(int device_id, int gpio_fd,
                            int device_id_ref, const char *edge);
    void unregister_interrupt(int device_id);

    // ── 中断处理（由 DevicePollingThread 的 epoll 循环调用）──
    void handle(int gpio_fd);

    // ── 软件消抖 ──
    void set_debounce_ms(int ms);

private:
    struct InterruptEntry {
        int      device_id;
        int      gpio_fd;
        int      last_value;           // 上次电平值（消抖用）
        uint64_t last_edge_time;       // 上次边沿时间（消抖用）
    };

    // fd → 中断条目 的映射表
    std::unordered_map<int, InterruptEntry>  entries_;

    int          debounce_ms_;              // 消抖时间（默认 20ms）
    UpstreamMessageQueue *upstream_queue_;
    DeviceStatusCache    *device_cache_;
};
```

#### 5.2 中断处理流程

中断处理的核心挑战是"消抖"——机械开关（如门禁触点）在闭合或断开的瞬间会产生多次电平抖动，如果不对抖动进行过滤，一次开关动作可能触发数十条告警消息。InterruptEventHandler 采用软件消抖方案：两次边沿事件间隔小于 debounce_ms_（默认 20ms）的视为同一次动作，只处理第一次。

```cpp
void InterruptEventHandler::handle(int gpio_fd) {
    auto it = entries_.find(gpio_fd);
    if (it == entries_.end()) return;

    InterruptEntry &entry = it->second;

    // 读取当前电平值
    uint8_t value;
    ssize_t n = read(gpio_fd, &value, sizeof(value));
    if (n != sizeof(value)) return;

    // 重置 sysfs 中断文件（读完后需要 seek 到开头才能再次读取）
    lseek(gpio_fd, 0, SEEK_SET);

    // ── 软件消抖 ──
    uint64_t now = get_monotonic_ms();
    if (now - entry.last_edge_time < (uint64_t)debounce_ms_) {
        // 抖动，忽略
        return;
    }

    int logical_value = (value != 0) ? 1 : 0;
    if (logical_value == entry.last_value) {
        // 电平未变化，忽略
        return;
    }

    entry.last_edge_time = now;
    entry.last_value = logical_value;

    // ── 更新设备状态缓存 ──
    DeviceStatus status;
    if (device_cache_->get(entry.device_id, &status)) {
        status.switch_state = (logical_value != 0);
        status.value = logical_value;
        status.last_update = get_monotonic_us();
        device_cache_->update(entry.device_id, status);
    }

    // ── 构造告警消息 ──
    LayerMessage event;
    event.type = MSG_DEVICE_EVENT;
    event.device_id = entry.device_id;
    event.timestamp = get_monotonic_us();

    DeviceEventPayload payload;
    payload.device_id = entry.device_id;
    payload.event_type = DEVICE_STATE_CHANGE;
    payload.new_value = logical_value;
    payload.timestamp = event.timestamp;

    event.payload = malloc(sizeof(DeviceEventPayload));
    memcpy(event.payload, &payload, sizeof(DeviceEventPayload));
    event.payload_len = sizeof(DeviceEventPayload);

    // 写入上行消息队列，由业务层 MessageProcessor 处理
    upstream_queue_->push(event);

    LOG_INFO("Interrupt", "Device %d state changed to %d",
             entry.device_id, logical_value);
}
```

中断处理的关键设计点有三个。第一，中断处理函数在 DevicePollingThread 的 epoll 循环中被调用，与轮询共享同一个线程，不存在额外的线程同步开销。第二，消抖采用"时间窗口"方案而非"延时等待"方案——后者需要阻塞线程等待抖动结束，会打断轮询；前者只记录时间戳做比较，零阻塞。第三，中断触发后立即更新 DeviceStatusCache，确保业务层查询到的是最新状态，而不是等到下一次轮询才更新。

中断事件的注册在系统启动时完成。GPIODriver 在 init 阶段检查设备配置中的 interrupt_enabled 字段，如果为 true，则调用 setup_interrupt 配置 GPIO 边沿触发，获取 epoll fd，注册到 InterruptEventHandler。DevicePollingThread 将中断 fd 加入自己的 epoll 监听集合，中断事件到达时 epoll 通知 DevicePollingThread，后者调用 InterruptEventHandler::handle 处理。

### 六、HardwareAbstractionLayer 硬件抽象层

HardwareAbstractionLayer（HAL）是数据访问层内部的一个独立子系统，负责将三款芯片（RK3568/RK3576/RK3588）的硬件差异封装为统一接口。HAL 对上为业务层（AI 推理线程、预处理器）和表示层（视频解码器）提供芯片无关的硬件操作接口，对下封装具体芯片的驱动调用细节。

```cpp
class RK3568NPUDriver : public NPUDriver {
public:
    bool load_model(const char *model_path, int *out_model_id) override {
        rknn_context ctx;
        int ret = rknn_init(&ctx, (void*)model_path, 0, 0, nullptr);
        if (ret < 0) return false;

        *out_model_id = ctx;
        models_[ctx] = {model_path, RKNN_NPU_INT8};
        return true;
    }

    int run_inference(int model_id, const uint8_t *input_data,
                      size_t input_len, void *output_buf,
                      size_t *output_len) override {
        uint64_t start = get_monotonic_ms();

        // 设置输入
        rknn_input inputs[1];
        memset(inputs, 0, sizeof(inputs));
        inputs[0].index = 0;
        inputs[0].type = RKNN_TENSOR_UINT8;
        inputs[0].size = input_len;
        inputs[0].fmt = RKNN_TENSOR_NHWC;
        inputs[0].buf = (void*)input_data;
        rknn_inputs_set(model_id, 1, inputs);

        // 执行推理
        rknn_run(model_id, nullptr);

        // 获取输出
        rknn_output outputs[1];
        memset(outputs, 0, sizeof(outputs));
        outputs[0].want_float = false;
        rknn_outputs_query(model_id, 1, outputs, nullptr);

        memcpy(output_buf, outputs[0].buf, outputs[0].size);
        *output_len = outputs[0].size;

        rknn_outputs_release(model_id, 1, outputs);

        return (int)(get_monotonic_ms() - start);
    }

    void unload_model(int model_id) override {
        rknn_destroy(model_id);
        models_.erase(model_id);
    }

private:
    struct ModelRecord {
        std::string path;
        int         quant_type;       // RKNN_NPU_INT8 / RKNN_NPU_FP16
    };
    std::unordered_map<int, ModelRecord> models_;
};
```

RK3588NPUDriver 的实现则利用三核 NPU 的并行能力，支持同时加载多个模型分配到不同 NPU 核心上执行：

```cpp
class RK3588NPUDriver : public NPUDriver {
public:
    bool load_model(const char *model_path, int *out_model_id) override {
        rknn_context ctx;

        // 选择负载最低的核心
        int core = select_least_loaded_core();

        rknn_init_extend extend;
        extend.core_mask = (1 << core);    // 指定 NPU 核心

        int ret = rknn_init(&ctx, (void*)model_path, 0,
                            RKNN_FLAG_ASYNC_MASK, &extend);
        if (ret < 0) return false;

        *out_model_id = ctx;
        core_assignment_[ctx] = core;
        core_load_[core]++;
        return true;
    }

    int run_inference(int model_id, const uint8_t *input_data,
                      size_t input_len, void *output_buf,
                      size_t *output_len) override {
        // 异步推理：rknn_run 立即返回，通过 rknn_wait 等待完成
        // 支持多核并行推理，不同模型在不同核心上同时执行
        // ...（实现与 RK3568 类似，增加核心选择和异步等待逻辑）
    }

private:
    int select_least_loaded_core() {
        int min_load = INT_MAX;
        int best_core = 0;
        for (int i = 0; i < 3; i++) {
            if (core_load_[i] < min_load) {
                min_load = core_load_[i];
                best_core = i;
            }
        }
        return best_core;
    }

    int core_load_[3] = {0, 0, 0};       // 三个 NPU 核心的当前负载
    std::unordered_map<int, int> core_assignment_;
};
```

### 七、DeviceStatusCache 在数据访问层的维护

DeviceStatusCache 作为层间交互类，其类定义在之前的文档中已详细描述。本节聚焦于数据访问层如何维护这个共享缓存。

DevicePollingThread 是 DeviceStatusCache 的唯一写入者。每次设备轮询成功后，线程立即调用 DeviceStatusCache::update 更新对应设备的状态；批量轮询完成后（一轮时间轮扫描结束），可以调用 batch_update 一次性写入多个设备的状态，减少读写锁的获取次数。

```cpp
// 在 execute_polling_round 中，轮询成功后的缓存更新
void DevicePollingThread::handle_poll_success(int device_id,
                                               const DeviceStatus &status) {
    DeviceStatus cached = status;
    cached.last_update = get_monotonic_us();
    cached.online = true;

    // 单设备更新（实时性要求高的设备，如门禁）
    device_cache_->update(device_id, cached);
}

// 一轮扫描结束后的批量更新（适用于低频设备）
void DevicePollingThread::batch_update_cache(
        const std::vector<DeviceStatus> &statuses) {
    device_cache_->batch_update(statuses.data(), statuses.size());
}
```

DeviceStatusCache 通过 pthread_rwlock_t 读写锁保护并发访问。数据访问层的轮询线程是唯一的写者，获取写锁更新状态；业务层和表示层是读者，获取读锁查询状态。读写锁的"多读单写"特性使得多个查询可以并发执行，只在写入时互斥，非常适合"读多写少"的传感器状态缓存场景。

设备离线标记（mark_offline）是 DeviceStatusCache 的另一个关键写入路径。当设备连续超时超过阈值时，DevicePollingThread 调用 mark_offline 将设备的 online 字段置为 false，同时保留最后一次已知的状态值（如最后读取的温度值），供上层查询时参考。

### 八、启动序列与运行时调度

#### 8.1 启动序列

```
├─③ 创建设备驱动实例

│     DeviceDriver *driver = config_manager->create_driver(device.id)
│     driver->init(device.config)
│     │
│     ├─ GPIODriver::init:
│     │   gpio_export() → gpio_set_direction() → 打开 value fd
│     │   if interrupt_enabled:
│     │     gpio_set_edge() → 注册到 InterruptEventHandler
│     │
│     ├─ ModbusRTUDriver::init:
│     │   open("/dev/ttySx") → 配置波特率/数据位/停止位/校验
│     │   rs485_enable_receiver()
│     │
│     ├─ I2CDriver::init:
│     │   open("/dev/i2c-N") → 设置从站地址
│     │
│     └─ SPIDriver::init:
│         open("/dev/spidevM.N") → 配置 SPI 模式/频率
│
├─④ 初始化总线互斥表
│   for each unique bus in config:
│     bus_mutex_table_[bus] = {PTHREAD_MUTEX_INITIALIZER, bus, -1}
│
├─⑤ 构建时间轮
│   rebuild_time_wheel()
│   for each device:
│     time_wheel_.push_back({device.id, driver, poll_interval,
│                            now + random_jitter, 0, true})
│   （random_jitter 避免所有设备同时首次轮询造成总线拥堵）
│
├─⑥ 初始化 epoll（用于中断 fd 监听）
│   epoll_fd_ = epoll_create1(0)
│   for each interrupt-enabled device:
│     epoll_ctl(epoll_fd_, EPOLL_CTL_ADD, gpio_fd, &ev)
│
└─⑦ 启动轮询线程
    pthread_create(&thread_, nullptr, polling_thread_entry, this)
```

启动序列中有一个值得注意的细节：时间轮中每个设备的首次轮询时间加入了随机抖动（random_jitter）。如果所有设备的首次轮询时间都设为 now + interval，那么所有设备会在启动后几乎同时触发第一次轮询，对于 RS485 总线上的多个 Modbus 设备会造成总线拥堵（多个请求排队等待）。随机抖动将首次轮询时间分散到 [now, now + interval) 区间内，平滑了初始负载。

### 十、技术要点与注意事项

**10.1 非阻塞轮询的两种模式**

数据访问层的设备轮询存在两种模式，取决于通信总线的速度。对于 GPIO 和 I2C 等快速总线，read_nonblock 在一次调用中完成读写并返回 DRIVER_OK，这是"同步快速"模式。对于 RS485 Modbus 等慢速总线，read_nonblock 第一次调用发送请求后返回 DRIVER_PENDING，后续通过 is_ready 检查完成状态，这是"异步慢速"模式。DevicePollingThread 的时间轮调度器统一处理这两种模式：对于 DRIVER_OK 的设备立即更新缓存并推进下次轮询时间；对于 DRIVER_PENDING 的设备，在后续循环迭代中检查完成状态，完成后再更新缓存。

**10.2 总线互斥的粒度设计**

总线互斥不是简单的"全局锁"，而是按总线类型和编号细分。同一块 RS485 芯片上的多个从站共享一把互斥锁，但不同 RS485 芯片（如 RS485_1 和 RS485_2）的锁相互独立，可以并行通信。I2C 同理，I2C_0 和 I2C_1 是独立的两条总线。GPIO 的互斥粒度最细——每个 GPIO 引脚独立，因为 GPIO 操作是内存映射的寄存器读写，不存在总线竞争。SPI 的互斥粒度是片选信号（CS），同一 SPI 控制器下不同 CS 的设备可以并行。

**10.3 中断与轮询的协作**

对于配置了中断的关键设备（如门禁），中断驱动和轮询同时存在。中断提供毫秒级的状态变化检测，轮询提供周期性的状态确认。两者并不冲突——中断负责"第一时间发现变化"，轮询负责"持续确认当前状态"。如果中断机制出现故障（如 GPIO 中断配置丢失），轮询仍然能在 500ms 内检测到状态变化，保证系统不会完全失去监控。

**10.4 热加载的安全性**

配置热加载涉及三个并发操作：轮询线程正在读取设备、热加载正在替换配置、业务层正在查询设备列表。DeviceConfigManager 通过读写锁保护 entries_ 的安全性：热加载时获取写锁（阻塞轮询线程的读取），轮询和查询时获取读锁（互不阻塞）。热加载完成后通过回调通知 DevicePollingThread 重建时间轮，重建过程也在 wheel_mutex_ 保护下进行。

**10.5 芯片升级的透明性**

HAL 的设计目标是让芯片升级对上层完全透明。当系统从 RK3568 升级到 RK3588 时，HAL 的 init 方法检测到新芯片型号，自动创建 RK3588NPUDriver 实例（三核 NPU 并行），业务层的 AIInferenceEngine 不需要修改任何代码，只需调用 NPUDriver::load_model 和 run_inference 即可。唯一的差异是 RK3588 的 NPU 利用率更高、推理更快，但这些差异体现在性能数据上，不需要上层代码做适配。同理，VideoDecoderDriver 和 RGADriver 的升级也是自动的。
