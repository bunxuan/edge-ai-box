### 二、ProtocolIOThread 核心调度机制

ProtocolIOThread 是表示层的心脏，也是整个系统与外部通信的唯一网络线程。它基于 Linux epoll 机制实现 I/O 多路复用，在单线程内统一调度所有网络协议的异步读写和所有摄像头的帧采集请求。

#### 2.1 epoll 事件循环设计

```cpp
class ProtocolIOThread {
public:
    ProtocolIOThread(
        FrameDispatcher        *frame_dispatcher,       // 帧数据出口
        UpstreamMessageQueue   *upstream_queue,         // 上行消息出口
        DownstreamMessageQueue *downstream_queue,       // 下行消息入口
        DeviceStatusCache      *device_cache            // 设备状态缓存（只读）
    );

    void start();   // 启动线程
    void stop();    // 停止线程（优雅退出）

    // 供 ProtocolConfigManager 调用：运行时注册/注销协议
    void register_protocol(ProtocolBase *proto);
    void unregister_protocol(ProtocolBase *proto);

    // 供 CameraConnectionManager 调用：注册/注销摄像头 fd
    void register_camera_fd(int fd, CameraInstance *cam);
    void unregister_camera_fd(int fd);

private:
    void event_loop();                    // epoll 主循环
    void dispatch_readable(int fd);       // 分发可读事件
    void dispatch_writable(int fd);       // 分发可写事件
    void process_downstream_messages();   // 处理下行消息（取出→写入 socket）
    void process_camera_timers();         // 处理摄像头定时拉帧

    int                          epoll_fd_;
    struct epoll_event           events_[64];     // 单次最多处理 64 个事件
    int                          timeout_ms_;      // epoll_wait 超时（50ms）

    // fd → 处理器 的映射表
    std::unordered_map<int, ProtocolBase*>    fd_to_protocol_;
    std::unordered_map<int, CameraInstance*>  fd_to_camera_;

    // 层间通道指针
    FrameDispatcher        *frame_dispatcher_;
    UpstreamMessageQueue   *upstream_queue_;
    DownstreamMessageQueue *downstream_queue_;

    // 心跳标记（供看门狗检查）
    std::atomic<uint64_t>   heartbeat_;
};
```

event_loop 是整个表示层的核心调度函数，每次迭代的完整流程如下：

```
event_loop() 单次迭代：
│
├─① epoll_wait(epoll_fd_, events_, 64, timeout_ms_=50)
│   等待最多 50ms，返回就绪的 fd 事件列表
│   如果返回 0（超时），跳到步骤④
│
├─② 遍历就绪事件，分发网络 I/O
│   for each event in events_:
│     if event 来自已注册协议 fd:
│       if EPOLLIN  → dispatch_readable(fd)
│       if EPOLLOUT → dispatch_writable(fd)
│       if EPOLLERR → 协议错误处理，触发重连
│     if event 来自摄像头 fd:
│       if EPOLLIN  → 摄像头数据就绪，读取帧数据
│
├─③ process_downstream_messages()
│   从 DownstreamMessageQueue 批量取出待发消息
│   按消息类型路由到对应协议适配器发送：
│     MSG_REPORT_DETECTION  → MQTTClientAdapter::publish()
│     MSG_REPORT_ANOMALY    → HTTPClientAdapter::upload_anomaly_image()
│     MSG_REPORT_LOG        → HTTPClientAdapter::upload_log_archive()
│     MSG_REPORT_STATUS     → MQTTClientAdapter::publish() 或 HTTPServerAdapter::respond()
│     MSG_REPORT_CMD_RESULT → MQTTClientAdapter::publish() 或 HTTPServerAdapter::respond()
│
├─④ process_camera_timers()
│   检查各路摄像头的定时拉帧是否到期
│   到期则发起 ONVIF 快照请求或检查 RTSP 帧就绪
│
└─⑤ 更新心跳标记
    heartbeat_.store(now_ms())
```

这个循环的关键设计点有三个。第一，epoll_wait 的超时设为 50ms，这意味着即使没有任何网络事件，循环也会每 50ms 唤醒一次检查下行消息队列和摄像头定时器，保证下行消息的发送延迟不超过 50ms。第二，所有 socket 都设置为非阻塞模式（O_NONBLOCK），任何读写操作遇到 EAGAIN/EWOULDBLOCK 立即返回，绝不阻塞整个循环。第三，下行消息的处理（步骤③）放在网络事件分发（步骤②）之后，这样每次循环迭代先收后发，符合网络编程的最佳实践。

#### 2.2 fd 到处理器的映射

epoll 模型的核心挑战是"事件到达时如何知道该交给谁处理"。本系统通过两张映射表解决：fd_to_protocol_ 将协议 socket 的 fd 映射到对应的 ProtocolBase 子类实例，fd_to_camera_ 将摄像头连接 fd 映射到 CameraInstance 实例。当 epoll 返回某个 fd 的可读事件时，event_loop 查表找到对应的处理器，调用其 on_readable() 方法。

这种设计使得新增协议类型时只需：(1) 创建 ProtocolBase 的新子类；(2) 在初始化时将新协议的 fd 注册到 epoll 和映射表中。event_loop 的代码完全不需要修改，符合开闭原则。

### 三、ProtocolBase 抽象基类与协议适配器

#### 3.1 ProtocolBase 统一事件接口

所有协议适配器（MQTT Client/Server、HTTP Server/Client）都继承自 ProtocolBase 抽象基类。ProtocolBase 定义了统一的事件接口，ProtocolIOThread 的 epoll 循环通过这些接口与各协议交互，不需要了解每个协议的具体实现细节。

```cpp
class ProtocolBase {
public:
    virtual ~ProtocolBase() = default;

    // ── 生命周期 ──
    virtual bool init(const JsonObject &config) = 0;     // 初始化（读取配置）
    virtual bool start() = 0;                             // 启动（建立连接/监听）
    virtual void stop() = 0;                              // 停止（断开连接/关闭监听）

    // ── epoll 事件回调（由 ProtocolIOThread 调用）──
    virtual void on_readable(int fd) = 0;                 // fd 可读时的处理
    virtual void on_writable(int fd) = 0;                 // fd 可写时的处理
    virtual void on_error(int fd, int errcode) = 0;       // 错误处理

    // ── 查询接口 ──
    virtual int   get_fd() const = 0;                     // 返回注册到 epoll 的主 fd
    virtual bool  has_pending_write() const = 0;          // 是否有待发数据
    virtual const char* protocol_name() const = 0;        // 协议名称（日志用）

    // ── 主动发送（由 ProtocolIOThread 的 process_downstream_messages 调用）──
    virtual bool accept_message(const LayerMessage &msg) = 0;  // 判断是否接受该消息
    virtual int  send_pending() = 0;                       // 执行一次发送，返回已发送字节数

protected:
    UpstreamMessageQueue   *upstream_queue_;     // 上行消息出口（子类直接写入）
    DownstreamMessageQueue *downstream_queue_;   // 下行消息入口（子类不直接使用）
    FrameDispatcher        *frame_dispatcher_;   // 帧分发器（仅摄像头相关协议使用）
};
```

accept_message() 方法是一个过滤机制——ProtocolIOThread 从 DownstreamMessageQueue 取出消息后，依次询问每个已注册协议"你是否需要发送这条消息"。MQTTClientAdapter 接受 MSG_REPORT_DETECTION 和 MSG_REPORT_STATUS 等消息，HTTPClientAdapter 接受 MSG_REPORT_ANOMALY 和 MSG_REPORT_LOG 等消息，HTTPServerAdapter 只接受与待响应 HTTP 请求关联的消息。这种设计避免了消息类型与协议之间的硬编码耦合。

#### 3.2 MQTTClientAdapter 实现

MQTTClientAdapter 作为 MQTT 客户端连接物联网云平台，负责上行检测结果和设备状态、下行接收云端管理指令。

```cpp
class MQTTClientAdapter : public ProtocolBase {
public:
    bool init(const JsonObject &config) override;
    bool start() override;
    void stop() override;

    void on_readable(int fd) override;
    void on_writable(int fd) override;
    void on_error(int fd, int errcode) override;

    int  get_fd() const override { return mqtt_socket_; }
    bool has_pending_write() const override;
    const char* protocol_name() const override { return "MQTT-Client"; }

    bool accept_message(const LayerMessage &msg) override;
    int  send_pending() override;

    // ── 专用发送方法 ──
    bool publish_detection(int camera_id, const DetectionResult &result);
    bool publish_device_status(const DeviceStatus &status);
    bool publish_alert(const char *alert_type, const char *detail);

    // ── 连接管理 ──
    void schedule_reconnect();       // 调度重连（指数退避）

private:
    void handle_mqtt_message(const char *topic, const uint8_t *payload, int len);
    void parse_cloud_command(const char *topic, const uint8_t *payload, int len);
    bool mqtt_connect();             // 建立 MQTT 连接（含 TLS 握手）
    void mqtt_disconnect();

    // ── MQTT 协议状态 ──
    enum class MqttState {
        DISCONNECTED,                // 未连接
        TLS_HANDSHAKING,             // TLS 握手中
        MQTT_CONNECTING,             // MQTT CONNECT 报文发送中
        CONNECTED,                   // 已连接，正常工作
        RECONNECTING                 // 等待重连（指数退避中）
    };

    int              mqtt_socket_;
    MqttState        state_;
    mqtt_client_t    mqtt_client_;          // MQTT-C 客户端结构体
    uint8_t         *send_buf_;             // MQTT 发送缓冲区（4KB）
    uint8_t         *recv_buf_;             // MQTT 接收缓冲区（4KB）

    // ── TLS 配置 ──
    mbedtls_ssl_context  ssl_ctx_;
    mbedtls_ssl_config   ssl_conf_;
    mbedtls_x509_crt     ca_cert_;

    // ── 订阅主题列表 ──
    struct SubTopic {
        std::string topic;
        int         qos;
    };
    std::vector<SubTopic>  subscriptions_;

    // ── 重连参数 ──
    int         reconnect_delay_sec_;       // 当前重连间隔（指数退避）
    int         max_reconnect_delay_sec_;   // 最大重连间隔（60秒）
    uint64_t    next_reconnect_time_;       // 下次重连时间

    // ── 配置 ──
    std::string broker_host_;
    int         broker_port_;
    std::string client_id_;
    std::string username_;
    std::string password_;
    std::string publish_prefix_;            // 发布主题前缀
};
```

**状态机流转**是 MQTTClientAdapter 的核心设计。MQTT 连接不是简单的"连上就用"，而是需要经历多个异步阶段：TCP 连接 → TLS 握手 → MQTT CONNECT/CONNACK → 订阅主题 → 正常工作。每个阶段都可能因为网络问题失败，需要重连。状态机确保每个阶段只在正确的时机执行，失败后从断点恢复而非从头开始。

```
状态机流转：

  DISCONNECTED ──(启动/定时重连)──→ TLS_HANDSHAKING
       ↑                                  │
       │                          TLS 握手成功 │ TLS 握手失败
       │                                  ↓         │
       │                          MQTT_CONNECTING   │
       │                                  │         │
       │                       CONNACK 收到 │    记录日志，
       │                                  ↓         │
       │                              CONNECTED     │
       │                             ╱       ╲      │
       │                  网络断开 ╱         ╲ 心跳超时
       │                         ↓           ╲      │
       │                   RECONNECTING       ╲     │
       │                     │    ↑            ╲    │
       │              退避等待 │    │ 重连尝试    ╲   │
       └─────────────────────┘    └───────────────→ (回到 TLS_HANDSHAKING)
```

**on_readable 实现**的关键逻辑：当 epoll 通知 mqtt_socket_ 可读时，根据当前状态执行不同操作。DISCONNECTED 状态不处理可读事件；TLS_HANDSHAKING 状态调用 mbedtls_ssl_handshake() 推进一步；CONNECTED 状态调用 MQTT-C 的 mqtt_sync() 函数处理收到的 MQTT 报文。如果收到 PUBLISH 报文（云端下发的管理指令），MQTT-C 会触发用户注册的回调函数，回调中调用 handle_mqtt_message() 解析主题和内容，封装为 LayerMessage 写入 UpstreamMessageQueue。

**云端管理指令解析**：handle_mqtt_message() 根据主题名区分指令类型。例如主题 /device/{client_id}/cmd/model_update 表示模型更新通知，解析 payload 中的模型 URL 和版本号后封装为 MSG_CLOUD_CMD_MODEL_UPDATE 消息；主题 /device/{client_id}/cmd/camera_config 表示摄像头配置变更，解析后封装为 MSG_CLOUD_CMD_CAMERA_CONFIG 消息。所有云端指令统一封装为 LayerMessage 后写入 UpstreamMessageQueue，由业务层 MessageProcessor 统一处理。

**accept_message 过滤逻辑**：

```cpp
bool MQTTClientAdapter::accept_message(const LayerMessage &msg) {
    switch (msg.type) {
        case MSG_REPORT_DETECTION:     // AI 检测结果上报
        case MSG_REPORT_STATUS:        // 设备状态上报
        case MSG_REPORT_CMD_RESULT:    // 控制命令执行结果
        case MSG_REPORT_MODEL_STATUS:  // 模型更新状态
        case MSG_REPORT_LOG:           // ERROR 级别日志即时推送
            return true;
        // 以下消息由 HTTPClientAdapter 处理，MQTT 不接收
        // MSG_REPORT_ANOMALY  → HTTP 上传异常图片
        // MSG_REPORT_CAPTURE  → HTTP 上传抓拍图片
        // MSG_REPORT_LOG_BATCH → HTTP 批量日志上传
        default:
            return false;
    }
}
```

#### 3.3 MQTTServerAdapter 实现

MQTTServerAdapter 作为轻量 MQTT 服务端，接收各个 ESP32/PLC 控制客户端的连接，采集其上报的传感器数据。

```cpp
class MQTTServerAdapter : public ProtocolBase {
public:
    bool init(const JsonObject &config) override;
    bool start() override;
    void stop() override;

    void on_readable(int fd) override;
    void on_writable(int fd) override;
    void on_error(int fd, int errcode) override;

    int  get_fd() const override { return listen_fd_; }
    bool has_pending_write() const override { return false; }  // 服务端无需主动发送
    const char* protocol_name() const override { return "MQTT-Server"; }

    bool accept_message(const LayerMessage &msg) override { return false; }
    int  send_pending() override { return 0; }

private:
    void on_new_client(int listen_fd);          // 接受新的 ESP32 连接
    void on_client_readable(int client_fd);     // 处理客户端上报数据
    void on_client_disconnect(int client_fd);   // 客户端断开
    void handle_sensor_report(int client_fd,
                              const char *topic,
                              const uint8_t *payload, int len);

    int listen_fd_;                              // 监听 socket

    // 已连接的客户端管理
    struct ClientInfo {
        int         fd;
        std::string client_id;        // ESP32 设备 ID
        uint64_t    last_active;      // 最后活跃时间
        mqtt_client_t mqtt_ctx;       // 每个客户端独立的 MQTT 上下文
    };
    std::unordered_map<int, ClientInfo>  clients_;

    int  max_clients_;                // 最大客户端数量（默认 32）
    int  client_timeout_sec_;         // 客户端超时（120 秒无活动视为离线）
};
```

MQTTServerAdapter 的 on_readable 需要区分两种情况：如果可读的 fd 是 listen_fd_（监听 socket），说明有新的 ESP32 客户端连入，调用 on_new_client 执行 accept；如果可读的 fd 是某个已连接客户端的 fd，说明该客户端上报了数据，调用 on_client_readable 处理。实现上通过判断 fd 是否等于 listen_fd_ 来区分。

on_client_readable 内部调用 MQTT-C 的服务端解析逻辑处理收到的 MQTT 报文。当收到 ESP32 上报的传感器数据（PUBLISH 报文）时，解析主题和 payload，封装为 MSG_SENSOR_DATA 类型的 LayerMessage 写入 UpstreamMessageQueue。同时更新 ClientInfo.last_active 时间戳。

客户端超时检测在 process_camera_timers 的同级位置（event_loop 的每次迭代中）执行：遍历 clients_ 表，如果某客户端超过 client_timeout_sec_ 未活跃，主动断开连接并记录日志。

#### 3.4 HTTPServerAdapter 实现

HTTPServerAdapter 提供本地 RESTful API，供局域网内通过浏览器或调试工具访问设备状态和执行控制命令。


HTTPServerAdapter 的路由设计遵循 RESTful 规范。parse_and_route 方法解析 HTTP 请求的方法、路径和请求体后，分发到对应的处理函数。以 handle_post_control 为例：收到 POST /api/devices/3/control 请求后，解析请求体中的控制命令（如 {"cmd": "open_door"}），封装为 MSG_LOCAL_CONTROL 类型的 LayerMessage 写入 UpstreamMessageQueue，同时在 pending_requests_ 中记录该请求的 client_fd 和 request_id，等待业务层处理完毕后将结果通过 enqueue_response 写回 HTTP 客户端。

Token 鉴权通过 verify_token 方法实现：检查 HTTP 请求头中的 Authorization 字段是否包含正确的 Bearer Token。所有 API 请求都必须携带 Token，否则返回 401 Unauthorized。Token 在 JSON 配置文件中设定，支持通过 MQTT 云端指令远程更新。

#### 3.5 HTTPClientAdapter 实现

HTTPClientAdapter 是与物联网平台进行 HTTP 交互的客户端，负责异常图片上传、定时抓拍图片上传、日志批量上传、模型文件下载和 OTA 固件下载。它是表示层中实现最复杂的协议适配器，因为需要处理大文件传输、断点续传和分片上传。

```cpp
class HTTPClientAdapter : public ProtocolBase {
public:
    bool init(const JsonObject &config) override;
    bool start() override;
    void stop() override;

    void on_readable(int fd) override;
    void on_writable(int fd) override;
    void on_error(int fd, int errcode) override;

    int  get_fd() const override { return current_fd_; }
    bool has_pending_write() const override;
    const char* protocol_name() const override { return "HTTP-Client"; }

    bool accept_message(const LayerMessage &msg) override;
    int  send_pending() override;

    // ── 高层上传/下载接口（由 CloudTaskScheduler 调用）──
    int submit_upload(const char *url, const char *file_path,
                      const char *content_type, int priority);
    int submit_download(const char *url, const char *save_path,

    struct TransferTask {
        int         task_id;

        std::string url;
        std::string file_path;
        std::string content_type;

        // 断点续传状态

        DownloadCallback callback;
    };

    void start_next_task();
    void advance_state_machine();

    void build_http_request(TransferTask &task);
    void send_chunk(TransferTask &task);

    int              current_fd_;
    HttpState        state_;

    std::priority_queue<TransferTask,

    size_t  chunk_size_;                  // 每片大小（默认 64KB）
    size_t  max_retry_;                   // 最大重试次数（3次）

    mbedtls_ssl_context  ssl_ctx_;

    size_t                recv_offset_;   // 接收缓冲区的写入位置

    // ── 配置 ──
    std::string  platform_host_;
    int          platform_port_;
    std::string  api_token_;
};
```

HTTPClientAdapter 的核心设计是**非阻塞 HTTP 状态机**。传统的 HTTP 客户端库（如 libcurl 的 easy 接口）在发送请求时会阻塞等待响应，这在嵌入式环境中是不可接受的——一次大文件上传可能持续数分钟，如果阻塞就会冻结整个 ProtocolIOThread。状态机将一次 HTTP 请求拆分为多个小步骤，每步只在 socket 可写/可读时执行一小段，其余时间让出 CPU 给 epoll 循环中的其他协议。

```
状态机流转（以分片上传异常图片为例）：

  IDLE ──(取出上传任务)──→ DNS_RESOLVING
                               │
                          DNS 解析完成
                               ↓
                          CONNECTING ──(TCP 连接建立)──→ TLS_HANDSHAKING
                                                             │
                                                        TLS 握手完成
                                                             ↓
                                                       SENDING_HEADERS
                                                             │
                                                        请求头发送完成
                                                             ↓
           ┌─── (还有数据) ←── SENDING_BODY ──(分片发送) ──┘
           │                      │
           │                 全部发送完成
           │                      ↓
           │               RECEIVING_HEADERS
           │                      │
           │                 响应头解析完成
           │                      ↓
           │               RECEIVING_BODY
           │                      │
           │                 响应接收完成
           │                      ↓
           └── (断点续传) ──── DONE ──→ IDLE（启动下一个任务）
```

分片上传的实现：大文件（如异常图片、日志压缩包）被切分为 chunk_size_（默认 64KB）大小的片，每片作为一个独立的 HTTP POST 请求发送。请求头中携带 Content-Range 字段标明本片在文件中的偏移范围，服务端据此拼接。如果某片发送失败（网络中断），下次重传时只需从失败的片开始，已成功的片不需要重发。这就是断点续传的核心原理。

accept_message 过滤逻辑：HTTPClientAdapter 接受所有需要文件传输的消息。

```cpp
bool HTTPClientAdapter::accept_message(const LayerMessage &msg) {

        case MSG_REPORT_CAPTURE:       // 定时抓拍图片上传
        case MSG_REPORT_LOG_BATCH:     // 日志批量上传
        case MSG_CLOUD_CMD_MODEL_UPDATE:  // 模型文件下载
        case MSG_CLOUD_CMD_OTA:           // OTA 固件下载

    }
}
```

#### 4.3 OnvifSnapshotFetcher 实现

ONVIF 快照拉取是首选的采集方式，优势在于无需维持持续流连接，按需拉取单帧 JPEG，资源占用极低。

```cpp
class OnvifSnapshotFetcher {
public:
    OnvifSnapshotFetcher(const CameraConfig &config);
    ~OnvifSnapshotFetcher();

    // 发起一次快照请求（非阻塞）
    // 返回 0 表示请求已发出，等待 fd 可读
    // 返回 -1 表示发起失败
    int start_snapshot();

    // fd 可读时调用：读取 HTTP 响应，提取 JPEG 数据
    // 返回 true 表示成功获取一帧
    // 返回 false 表示读取失败（连接断开等）
    bool on_readable(int fd, uint8_t **out_data, size_t *out_len);

    int  get_fd() const { return socket_fd_; }

private:
    bool connect_nonblock();
    bool build_http_get_request();
    bool parse_http_response(const uint8_t *buf, size_t len,
                             uint8_t **jpeg_data, size_t *jpeg_len);
    bool parse_digest_auth_challenge(const uint8_t *buf, size_t len);
    bool build_digest_auth_request();

    int          socket_fd_;
    std::string  host_;
    int          port_;
    std::string  snapshot_path_;       // URL 路径（如 /onvif-http/snapshot）

    // Digest 认证状态
    bool         auth_required_;
    std::string  nonce_;
    std::string  realm_;
    int          auth_state_;          // 0=未认证, 1=已收到挑战, 2=已认证

    // 收发缓冲区
    std::vector<uint8_t>  send_buf_;
    std::vector<uint8_t>  recv_buf_;
};
```

OnvifSnapshotFetcher 的工作流程：start_snapshot 发起一次非阻塞的 HTTP GET 请求到摄像头的 ONVIF 快照 URL。如果摄像头需要 Digest 认证，首次请求会收到 401 响应，fetcher 解析出 nonce 和 realm，构建带 Digest 认证头的二次请求。认证成功后，后续的快照请求直接携带认证头。

每次快照请求的完整生命周期是：DNS 解析 → TCP 连接 → HTTP GET → 接收 JPEG → 关闭连接（或保持连接供下次复用）。整个过程中 socket 始终是非阻塞的，fd 注册在 ProtocolIOThread 的 epoll 中，由 epoll 循环驱动读写推进。

帧数据就绪后，on_readable 从 HTTP 响应体中提取 JPEG 数据，调用 CameraInstance::on_frame_received 封装为 VideoFrame 写入 FrameDispatcher。

#### 4.4 RtspStreamDecoder 实现

RTSP 流解码是 ONVIF 不可用时的回退方案。它维持一条持续的 RTSP 连接，通过硬件解码器获取连续的视频帧流。

```cpp
class RtspStreamDecoder {
public:
    RtspStreamDecoder(const CameraConfig &config,
                      VideoDecoderDriver *vdec_driver);  // HAL 视频解码器
    ~RtspStreamDecoder();

    // 建立 RTSP 连接（非阻塞）
    int start_stream();

    // fd 可读时调用：读取 RTP 数据，送入硬件解码器
    bool on_readable(int fd);

    // 解码出一帧后的回调
    void set_frame_callback(std::function<void(uint8_t*, size_t, int, int, PixelFormat)> cb);

    int  get_fd() const { return rtsp_socket_; }
    bool is_streaming() const { return streaming_; }

private:
    // ── RTSP 交互状态机 ──
    enum class RtspState {
        INIT,
        OPTIONS_SENT,
        DESCRIBE_SENT,
        SETUP_SENT,
        PLAY_SENT,
        STREAMING,
        TEARDOWN
    };

    void send_options();
    void send_describe();
    void send_setup();
    void send_play();
    void send_teardown();
    void parse_rtsp_response(const uint8_t *data, size_t len);

    // ── RTP 解包 ──
    void process_rtp_packet(const uint8_t *data, size_t len);
    void reassemble_nalu();                  // H.264/H.265 NAL 单元重组

    // ── 硬件解码 ──
    void feed_decoder(const uint8_t *nalu, size_t len);
    void on_decoded_frame(uint8_t *data, size_t len,
                          int width, int height, PixelFormat fmt);

    // ── 断线重连 ──
    void on_stream_error();
    bool reconnect();

    int              rtsp_socket_;
    RtspState        rtsp_state_;
    bool             streaming_;
    std::string      rtsp_url_;
    std::string      session_id_;          // RTSP Session ID

    // 硬件解码器（HAL 层）
    VideoDecoderDriver *vdec_driver_;

    // NAL 单元重组缓冲
    std::vector<uint8_t>  nalu_buffer_;
    uint32_t              current_timestamp_;

    // 帧回调
    std::function<void(uint8_t*, size_t, int, int, PixelFormat)> frame_callback_;

    // 抽帧控制
    uint64_t  last_extract_time_;
    int       frame_interval_ms_;          // 从 config 读取
};
```

RTSP 交互遵循标准的状态机流程：INIT → 发送 OPTIONS → 收到响应 → 发送 DESCRIBE（获取 SDP 媒体描述）→ 收到响应 → 发送 SETUP（协商 RTP 传输参数）→ 收到响应 → 发送 PLAY → 进入 STREAMING 状态。每个步骤都是非阻塞的，socket fd 注册在 epoll 中，每次可读时推进一步状态机。

进入 STREAMING 状态后，on_readable 持续接收 RTP 包，通过 process_rtp_packet 解包、reassemble_nalu 重组 NAL 单元，然后送入 HAL::VideoDecoderDriver 进行硬件解码。解码出的原始帧（NV12 格式）通过 frame_callback 回调给 CameraInstance，由 CameraInstance 按 frame_interval_ms 配置的间隔抽帧，封装为 VideoFrame 写入 FrameDispatcher。

断线重连逻辑：检测到 RTSP 连接断开（read 返回 0 或错误）后，先发送 TEARDOWN 清理会话，等待 2 秒后重新执行完整的 RTSP 交互流程。连续重连 5 次失败后标记该摄像头离线，通知 CameraConnectionManager。

#### 4.5 摄像头定时拉帧调度

CameraConnectionManager::check_frame_timers 由 ProtocolIOThread 在每次 epoll 循环迭代中调用，负责检查各路摄像头的定时拉帧是否到期。

```cpp
void CameraConnectionManager::check_frame_timers() {
    uint64_t now = get_monotonic_ms();
    for (auto &[id, cam] : cameras_) {
        if (!cam->is_connected()) continue;

        if (cam->is_capture_due()) {
            // 到达拉帧时刻，触发一次采集
            cam->trigger_frame_capture();
        }
    }
}

// CameraInstance 内部：
bool CameraInstance::is_capture_due() {
    return get_monotonic_ms() >= next_capture_time_;
}

void CameraInstance::trigger_frame_capture() {
    if (onvif_fetcher_) {
        onvif_fetcher_->start_snapshot();
        // ONVIF 快照是短连接请求，fd 注册到 epoll 后由事件驱动
    }
    // RTSP 是持续流，不需要主动触发，只需在 on_readable 中按间隔抽帧
    next_capture_time_ = get_monotonic_ms() + config_.frame_interval_sec * 1000;
}
```

对于 ONVIF 方式，每次 trigger_frame_capture 发起一次 HTTP GET 快照请求，请求完成后 fd 从 epoll 中注销（短连接），下次拉帧时重新注册。对于 RTSP 方式，连接是持续的，trigger_frame_capture 只更新 next_capture_time 时间戳，实际抽帧在 on_readable 中按时间间隔过滤。

UIManager 与 ProtocolIOThread 之间没有直接函数调用。UI 线程需要数据时主动去读：设备状态从 DeviceStatusCache 读取（读写锁的读端），告警消息从 DownstreamMessageQueue 读取（互斥锁保护的 pop）。这种"拉取"模式而非"推送"模式的设计，使得 UI 线程的渲染节奏完全自主，不会被网络事件的不均匀到达打乱。

### 八、关键技术实现说明

#### 8.1 非阻塞 I/O 的统一处理

表示层所有网络操作都遵循同一套非阻塞模式。以 read 操作为例：

```cpp
// 统一的非阻塞读取模式
ssize_t result = read(fd, buf, buf_size);
if (result > 0) {
    // 成功读取 result 字节，正常处理
    process_data(buf, result);
} else if (result == 0) {
    // 对端关闭连接
    on_connection_closed(fd);
} else {
    // result < 0
    if (errno == EAGAIN || errno == EWOULDBLOCK) {
        // 没有数据可读（非阻塞模式下的正常情况）
        // 不做任何处理，等下次 epoll 通知
    } else {
        // 真正的错误
        on_error(fd, errno);
    }
}
```

write 操作同理。关键点：永远不要因为 EAGAIN 而重试或等待，直接返回让 epoll 在下次可写时通知。这是保证 ProtocolIOThread 不阻塞的铁律。

#### 8.2 TLS 加密的异步化

MQTT 和 HTTPS 都需要 TLS 加密，而 TLS 握手本身是多轮次的（client hello → server hello → certificate → key exchange → finished），每次交互都需要一次 send + recv。在非阻塞模式下，TLS 握手必须拆分为多个步骤：

```cpp
// mbedTLS 非阻塞握手的处理
void MQTTClientAdapter::on_readable(int fd) {
    if (state_ == MqttState::TLS_HANDSHAKING) {
        int ret = mbedtls_ssl_handshake(&ssl_ctx_);
        if (ret == 0) {
            // 握手完成，进入 MQTT CONNECT 阶段
            state_ = MqttState::MQTT_CONNECTING;
            send_mqtt_connect();
        } else if (ret == MBEDTLS_ERR_SSL_WANT_READ) {
            // 需要更多数据，等下次 epoll 可读
            // 什么都不做
        } else if (ret == MBEDTLS_ERR_SSL_WANT_WRITE) {
            // 需要发送数据，注册 EPOLLOUT 事件
            epoll_modify_fd(fd, EPOLLIN | EPOLLOUT);
        } else {
            // TLS 握手失败
            LOG_ERROR("TLS handshake failed: %d", ret);
            schedule_reconnect();
        }
    }
}
```

mbedTLS 库通过返回 WANT_READ/WANT_WRITE 来告知调用者"我需要更多数据"或"我需要发送数据"，调用者据此注册相应的 epoll 事件，等下次事件到达时继续握手。这种模式使得 TLS 握手不会阻塞 epoll 循环。

#### 8.3 优雅退出机制

表示层的退出需要按顺序清理所有资源，避免文件描述符泄漏和线程挂起：

```
退出顺序：

① UIManager::stop()
   设置退出标志 → UI 线程检测到标志后退出循环 → join 等待 UI 线程结束

② 停止摄像头采集
   CameraConnectionManager::stop()
   → 所有 CameraInstance::stop()
   → ONVIF: 取消进行中的 HTTP 请求，关闭 socket
   → RTSP: 发送 TEARDOWN，关闭 socket
   → 从 epoll 中注销所有摄像头 fd

③ 停止协议适配器
   各 ProtocolBase::stop()
   → MQTTClientAdapter: 发送 MQTT DISCONNECT，关闭 socket
   → MQTTServerAdapter: 断开所有客户端连接，关闭 listen socket
   → HTTPServerAdapter: 断开所有连接，关闭 listen socket
   → HTTPClientAdapter: 取消所有进行中的传输任务，关闭 socket
   → 从 epoll 中注销所有协议 fd

④ ProtocolIOThread::stop()
   设置退出标志 → epoll 循环检测到标志后退出 → close(epoll_fd) → join 等待线程结束

⑤ 释放层间通道（由上层统一管理，表示层不拥有这些队列的所有权）
```

#### 8.4 错误恢复与重连策略

表示层涉及的所有长连接（MQTT Client、RTSP 流、HTTP Client 大文件传输）都实现了自动重连机制，但策略各有不同：

MQTTClientAdapter 采用指数退避重连：首次断开后等待 1 秒重试，第二次等待 2 秒，第三次 4 秒……最大等待 60 秒。每次成功连接后退避计时器重置。这种策略避免了网络故障时大量设备同时重连造成的"雷群效应"。

RtspStreamDecoder 采用固定间隔重连：断开后等待 2 秒重试，最多连续重试 5 次。超过 5 次后标记摄像头离线，通知 CameraConnectionManager。之所以不用指数退避，是因为 RTSP 摄像头的断线通常是本地网络问题（摄像头掉电、网线断开），等待再久也不会自动恢复，快速重试 5 次后放弃是更合理的策略。

HTTPClientAdapter 的传输任务采用应用层重试：每个任务最多重试 3 次，间隔 5s/15s/45s。断点续传保证重试时不需要从头传输已成功的部分。重试由 CloudTaskScheduler 统一调度，不阻塞其他任务。
